## 1. 引言：两种 Agent 形态的本质分歧

在深入任何具体模块之前，必须先理解 Codex 和 Claude Code 在**系统形态**上的根本差异。这个差异不是语言选择（Rust vs TypeScript），也不是功能多少，而是对"Agent 到底是什么"的不同回答。

博客第 5 篇给出了最精准的概括：

> **Claude Code 更像 "terminal-first agent application"。Codex 更像 "agent runtime + protocol + harness"。**

Claude Code 的核心是一个 `query()` async generator——一个在 TypeScript 运行时里流转的大型异步数据流。模型请求、工具执行、权限检查、UI streaming、compaction、memory prefetch 都在同一条运行时轨迹里协作。一个 `Tool` 的上下文不仅知道"如何执行"，还知道 AppState、UI 渲染函数、session 状态等运行时的很多东西。

Codex 则把自己拆成了一个**可被多个 client 驱动的 thread/turn runtime**。CLI/TUI/App Server/VS Code/remote client 都只是 client，它们通过 `thread/start`、`turn/start` 等协议边界进入 core。Core 里的 `Codex` 结构体是一个 **submission/event 队列对**：一边收 `Op`（操作），一边吐 `Event`（事件）。这是整个 Codex 架构的心脏。

这两种形态各有其适用阶段：

- **当产品主要是"人在终端里和 agent 结对"时**，Claude Code 的集成式 runtime 很自然，功能接入路径短，体验容易做整体。
- **当产品开始承担"后台任务、远程协作、长会话恢复、多 Agent 调度、日志审计"时**，Codex 的 harness 化就会越来越重要。

对 DeepOmni 来说，我们的目标是构建一个可复用的 agent harness。因此 Codex 的 submission/event 队列对模式是我们需要深入理解和借鉴的核心。

## 2. Codex 的 Turn Path：从用户输入到模型回流的完整链路

### 2.1 链路全景

博客第 1 篇花了大量篇幅描述了 Codex 的完整 turn path。把这条链路画出来：

```
codex.js (npm, 只负责找到 native binary)
  → Rust CLI (MultitoolCli, multitool 分发)
    → TUI (ChatWidget 只负责交互状态)
      → in-process App Server (AppServerTarget::Embedded)
        → ClientRequest::TurnStart (app-server protocol boundary)
          → Op::UserInputWithTurnContext (core submission)
            → Session (同一时刻最多一个 running task)
              → RegularTask::run (循环调用 run_turn)
                → build_prompt → model.stream → tool dispatch → EventMsg
                  → app-server notification/request (翻译层)
                    → TUI render (按 thread id 分流事件)
```

这条链路看起来很长，但**每一层都有明确的职责边界**。关键不在于层数多少，而在于这些层之间的**通信方式**。

### 2.2 核心抽象：Codex 是一个 Submission/Event 队列对

`Codex` 结构体（在 `core/src/session/mod.rs`）被源码注释描述为一个 queue pair。对应的源码结构：

```rust
// ref/codex: codex-rs/core/src/session/mod.rs
pub struct Codex {
    /// 发送 submission 到后台 session loop
    submission_tx: mpsc::UnboundedSender<Submission>,
    /// Session 后台循环的 JoinHandle
    session_handle: JoinHandle<()>,
}

impl Codex {
    pub fn spawn(config: SessionConfig) -> (Self, ConversationReceiver) {
        // 1. 创建 submission channel
        let (submission_tx, submission_rx) = mpsc::unbounded_channel();
        // 2. 创建 event channel（ConversationReceiver 是对 event_rx 的封装）
        let (tx_event, rx_event) = async_channel::unbounded();
        // 3. 启动后台 Session loop
        let session_handle = tokio::spawn(async move {
            let mut session = Session::new(config, submission_rx, event_tx);
            session.submission_loop().await;
        });
        (Self { submission_tx, session_handle }, event_rx)
    }

    pub fn submit(&self, op: Op) -> SubmissionId {
        let id = SubmissionId::new();
        self.submission_tx.send(Submission { id, op }).unwrap();
        id
    }
}
```

这个设计的核心特征：

1. **submit 只入队不等待**：调用方（TUI/App Server/remote client）提交一个 `Op`，拿到一个 `SubmissionId`，然后就可以回去了。不需要等 turn 完成。
2. **event 是异步回流**：所有结果（assistant delta、tool call、approval request、turn complete）都以 `EventMsg` 的形式从 event channel 流出。调用方订阅这个 channel 来消费事件。
3. **Session 是后台循环**：`submission_loop` 在一个独立的 tokio task 里跑，从 submission channel 取 Op，处理后发 Event。Session 自己维护状态（active task、history、tools 等），外界看不到也不需要知道。

### 2.3 Op 枚举：进入 Core 的窄门

`Op` 是外界能发给 core 的**唯一入口类型**。在源码中它是一个枚举：

```rust
// ref/codex: codex-rs/protocol/src/protocol.rs
pub enum Op {
    /// 纯用户输入（不带 turn 配置覆盖）
    UserInput {
        items: Vec<ResponseInputItem>,
    },
    /// 带 turn context override 的用户输入
    UserInputWithTurnContext {
        items: Vec<ResponseInputItem>,
        turn_context: TurnContextOverrides,
    },
    /// 审批决策
    ApprovalDecision {
        approval_id: String,
        decision: ReviewDecision,
    },
    /// 中断当前 task（不终止后台终端进程）
    Interrupt,
    /// 终止所有后台终端进程
    CleanBackgroundTerminals,
    /// 带完整 turn 配置的用户输入（用于 CodexThread）
    UserTurn {
        items: Vec<UserInput>,
        cwd: PathBuf,
        approval_policy: AskForApproval,
        sandbox_policy: SandboxPolicy,
        model: String,
        // effort, summary, service_tier, collaboration_mode, personality 等
    },
    /// 跨 agent 通信消息
    InterAgentCommunication { communication: InterAgentCommunication },
    /// 覆盖后续 turn 的持久化配置（不入队输入，只改默认值）
    OverrideTurnContext { cwd: Option<PathBuf>, approval_policy: Option<AskForApproval>, model: Option<String>, /* ... */ },
    /// 审批命令执行
    ExecApproval { id: String, turn_id: Option<String>, decision: ReviewDecision },
    /// 审批代码 patch
    PatchApproval { id: String, decision: ReviewDecision },
    /// 解决 MCP elicitation 请求
    ResolveElicitation { server_name: String, request_id: RequestId, decision: ElicitationAction },
    /// 回答 request_user_input 工具调用
    UserInputAnswer { id: String, response: RequestUserInputResponse },
    /// 回答 request_permissions 工具调用
    RequestPermissionsResponse { id: String, response: RequestPermissionsResponse },
    /// 回答 dynamic tool call
    DynamicToolResponse { id: String, response: DynamicToolResponse },
    /// 刷新 MCP server
    RefreshMcpServers { config: McpServerRefreshConfig },
    /// 重新加载用户配置
    ReloadUserConfig,
    /// 实时对话相关（Start / Audio / Text / Close / ListVoices）
    RealtimeConversationStart(ConversationStartParams),
    RealtimeConversationAudio(ConversationAudioParams),
    RealtimeConversationText(ConversationTextParams),
    RealtimeConversationClose,
    RealtimeConversationListVoices,
}
```

这里有一个非常关键的设计点：**用户输入和 turn 的运行配置是一起被提交的**。`TurnContextOverrides` 里包含了 cwd、approval policy、permission profile、model、reasoning effort、service tier、collaboration mode、personality 等运行时上下文。这意味着 agent 的行为不只由文本 prompt 决定，还由一整套运行时配置决定。

博客原文这样解释：

> 也就是说，用户输入和本 turn 的运行配置是一起被提交的。这个小细节很关键：agent 的行为不是只由文本 prompt 决定，还由 cwd、权限、沙箱、模型、协作模式等运行时上下文决定。

### 2.4 Session：同一时刻一个 Active Task

`Session` 是 submission_loop 的所有者。它的核心约束是：

> 一个 session 代表初始化后的 model agent，**同一时刻最多只有一个 running task**，可以被用户输入 interrupt 或 steer。

这个约束带来了两种处理路径：

1. **没有 active turn**：创建新 turn，启动 `RegularTask`。
2. **已有 active turn**：尝试 `steer_input`，把新用户输入导入当前 active turn。

steer 是一个很重要的能力：用户可以在 agent 执行过程中注入新的指示，而不需要等 turn 完成再重新提交。这只有在 submission/event 队列对的架构下才能自然实现——如果是同步调用链，用户输入必须等 `run_turn` 返回。

### 2.5 RegularTask 与 run_turn：Agent Loop 的心跳

`RegularTask::run` 是真正的 agent 循环入口。博客把它的控制流压缩成了伪代码：

```
emit TurnStarted
loop:
    prompt = build_prompt(history, visible_tools, turn_settings)
    stream = model.stream(prompt)
    for item in stream:
        if item is assistant delta:
            emit EventMsg delta
        if item is tool call:
            run tool through ToolRouter / ToolRegistry
            append tool output to history
            mark needs_follow_up
    if needs_follow_up:
        continue
    emit TurnComplete
    break
```

这里最重要的是 **`needs_follow_up`**。工具输出不是给 UI 看完就结束，而是会变成下一次模型请求的一部分。一个 turn 内部可以有**多次 model sampling**。这和 ReAct 论文里"reasoning traces 与 actions 交错进行"的思想是一脉相承的。

博客原文：

> run_turn 源码注释其实就是 agent loop 的最小定义。模型返回 function call 时，Codex 执行对应工具，并把工具输出加入下一次 sampling request。模型只返回 assistant message 时，把消息加入 conversation history，并认为 turn 完成。

### 2.6 事件回流：Core 只发 Event，不操作 UI

这是 Codex 架构中**最值得强调的设计原则**：core 不直接操作 TUI。它只发 `EventMsg`。

```rust
// ref/codex: core 侧
fn emit(&self, event: EventMsg) {
    self.event_tx.send(event).ok();
}

// ref/codex: app-server 侧 (翻译层, bespoke_event_handling.rs)
// 把 core 的 EventMsg 转成 app-server protocol 的 ServerNotification 或 ServerRequest
fn apply_bespoke_event_handling(event: EventMsg) -> AppServerProtocolEvent {
    match event {
        EventMsg::TurnStarted { .. }                => ServerNotification::TurnStarted { .. },
        EventMsg::AgentMessageContentDelta { .. }   => ServerNotification::AgentMessageDelta { .. },
        EventMsg::AgentReasoningDelta { .. }         => ServerNotification::AgentReasoningDelta { .. },
        EventMsg::ToolCallStarted { .. }             => ServerNotification::ToolCallStarted { .. },
        EventMsg::ToolCallCompleted { .. }           => ServerNotification::ToolCallCompleted { .. },
        EventMsg::TurnComplete { .. }                => ServerNotification::TurnCompleted { .. },
        EventMsg::TurnAborted { .. }                 => ServerNotification::TurnAborted { .. },
        // 需要 client 回答的事件走 ServerRequest 而不是 Notification：
        EventMsg::RequestExecApproval { .. }         => ServerRequest::ExecApproval { .. },
        EventMsg::RequestPatchApproval { .. }        => ServerRequest::PatchApproval { .. },
        EventMsg::RequestUserInput { .. }            => ServerRequest::ToolRequestUserInput { .. },
        EventMsg::RequestPermissions { .. }          => ServerRequest::RequestPermissions { .. },
    }
}

// ref/codex: TUI 侧
fn handle_app_server_event(event: AppServerEvent) {
    // 根据 thread_id 分流到对应 thread channel
    // active thread 的事件进入 ChatWidget 渲染
    // 非 active thread 的事件先 buffer
}
```

这个方向有一个很重要的安全含义：**审批不是 UI 自己推断出来的**。Core policy 计算出某个 command/patch/MCP tool 需要审批 → app-server 把它转成 `ServerRequest` → UI 展示给用户 → 用户决策回填 core。UI 只是呈现和收集决策，不应该重新实现一遍权限判断。

## 3. Claude Code 的 Query Loop：集成式 Runtime 的另一种选择

### 3.1 query() async generator

Claude Code 的核心循环不是 submission/event 队列对，而是一个 **async generator**：

```typescript
// ref/claude-code: src/query.ts
export async function* query(
    config: QueryEngineConfig
): AsyncGenerator<StreamEvent | Message> {
    // queryLoop 内部维护 mutable state
    let state = {
        messages: config.initialMessages,
        toolUseContext: buildToolUseContext(config),
        autoCompactTracking: new AutoCompactTracker(),
        turnCount: 0,
        pendingToolUseSummary: null,
        stopHookActive: false,
    };

    while (true) {
        // 1. 构造模型请求
        const response = await streamModelResponse(state);

        // 2. 处理流式响应
        for await (const event of response) {
            yield event; // 直接 yield 给调用方
        }

        // 3. 执行工具
        const executor = new StreamingToolExecutor(tools, canUseTool, state.toolUseContext);
        for (const toolBlock of response.toolBlocks) {
            executor.addTool(toolBlock, assistantMessage);
        }

        // 4. 收集工具结果
        for await (const update of executor.getRemainingResults()) {
            yield* update.messages;
        }

        // 5. 判断是否继续
        if (!hasToolUse) break;
        state.turnCount++;
    }
}
```

### 3.2 QueryEngineConfig：应用上下文的大合集

Claude Code 的 `QueryEngineConfig` 直接持有几类运行时状态：

```typescript
// ref/claude-code: src/QueryEngine.ts
interface QueryEngineConfig {
    // 工作区和输入
    cwd: string;
    initialMessages: Message[];
    fileCaches: Map<string, FileCache>;

    // 工具和扩展
    tools: Tools;
    commands: Command[];
    mcpClients: McpClient[];
    agents: Agent[];

    // 权限和 UI
    canUseTool: CanUseToolFn;
    getAppState: () => AppState;
    setAppState: (state: AppState) => void;
    permissionElicitation: PermissionElicitation;

    // 模型设置
    model: string;
    fallbackModel?: string;
    thinkingConfig: ThinkingConfig;
    budget: Budget;
    jsonSchema?: JSONSchema;
}
```

注意这里和 Codex 的 `Op` + `TurnContext` 的区别：Codex 把运行时配置从 core 中隔离出来，通过 `TurnContextOverrides` 在 turn start 时传入并冻结；Claude Code 则让整个应用运行时的状态（包括 UI 函数 `setAppState`、权限函数 `canUseTool`）直接进入 query loop。

### 3.3 StreamingToolExecutor：边流式边并行

Claude Code 的工具执行有一个 Codex 没有的特点：**工具可以在模型还在流式输出时就开始执行**。

```typescript
// ref/claude-code: src/services/tools/StreamingToolExecutor.ts
export class StreamingToolExecutor {
    private tools: TrackedTool[] = [];

    addTool(block: ToolUseBlock, assistantMessage: AssistantMessage): void {
        // 工具到达时立即判断是否可以开始执行
        const isConcurrencySafe = toolDefinition?.isReadOnly ?? false;
        this.tools.push({
            id: block.id,
            block,
            status: 'queued',
            isConcurrencySafe,
            pendingProgress: [],
        });
        this.maybeStartTools(); // 立即尝试启动
    }

    private maybeStartTools(): void {
        // concurrent-safe 工具可以并行执行
        // non-concurrent 工具必须独占执行
        for (const tool of this.tools) {
            if (tool.status !== 'queued') continue;
            if (tool.isConcurrencySafe && !this.hasExclusiveRunning()) {
                this.startTool(tool);
            } else if (!tool.isConcurrencySafe && !this.hasAnyRunning()) {
                this.startTool(tool);
            }
        }
    }
}
```

这种设计对延迟优化很有帮助：当模型输出多个工具调用时，第一个工具可以在模型还在输出第二个工具的 schema 时就开始执行。但代价是增加了并发控制的复杂度。

## 4. 核心概念对照：术语体系

博客第 1 篇专门花了一节来消歧义。这些术语在两个项目中的对应关系：

| 概念 | Codex | Claude Code | DeepOmni（当前） |
|------|-------|-------------|-------------------|
| 会话线 | `Thread` (有 ThreadId, 可持久化) | 隐式（messages 数组） | `Thread` (有 ThreadId, SQLite 持久化) |
| 一次用户任务 | `Turn` (一个 turn 内可有多次 model sampling) | `turnCount` (query loop 内的计数器) | `Turn` (一个 turn = 一次 submit_turn 调用) |
| 进入 core 的操作 | `Submission` (Op + SubmissionId) | 函数调用 (`query(config)`) | 方法调用 (`runtime.submit_turn()`) |
| 模型可见历史项 | `ResponseItem` (枚举: Message/FunctionCall/...) | `Message` (union type) | `ModelMessage` (role + content) |
| core 对外发出的事件 | `EventMsg` (枚举: TurnStarted/Delta/...) | `StreamEvent` (yield from generator) | `EventFrame` (枚举, 通过 EventBus broadcast) |
| 模型请求 | `Prompt` (input + tools + instructions + ...) | `streamModelResponse(state)` | `ModelRequest` (messages + tools + ...) |
| 工具结果 | `ResponseInputItem` (tool output) | `Message` (tool_result content) | `ToolOutput` |

这张表最重要的启示是：Codex 把 `Submission` 和 `Event` 作为**一等类型**严格定义，它们是 core 的唯一入口和唯一出口。而 Claude Code 和 DeepOmni 目前都没有这种严格的边界——进入 core 是函数调用，出来是返回值或 yield。

## 5. UserInput：UI/Core 之间的中间语言

博客第 1 篇提到了一个常被忽略的设计点：**Codex 不是把输入框里的字符串直接塞进模型**。

```
底部输入框 → InputResult::Submitted
  → ChatWidget 组装成 UserInput
    → UserInput 定义在 protocol/src/user_input.rs
      → 不只是纯文本，还包括 remote image、local image、skill、structured mention
        → Vec<UserInput> 转换成 ResponseInputItem::Message
          → skill / mention 不在这里展开，由 core 解析成更精确的上下文注入
```

`UserInput` 的类型定义：

```rust
// ref/codex: codex-rs/protocol/src/user_input.rs (实际源码)
#[non_exhaustive]
#[derive(Debug, Clone, Deserialize, Serialize, PartialEq)]
#[serde(tag = "type", rename_all = "snake_case")]
pub enum UserInput {
    /// 纯文本，可带 text_elements（字节范围标记，用于 UI rich input）
    Text {
        text: String,
        #[serde(default)]
        text_elements: Vec<TextElement>,
    },
    /// 预编码 data-URI 图片
    Image { image_url: String },
    /// 本地图片路径（序列化时转为 base64 data URL）
    LocalImage { path: PathBuf },
    /// 用户选择的 Skill（名字 + SKILL.md 路径）
    Skill { name: String, path: PathBuf },
    /// 结构化 mention（如 app://connector-id 或 plugin://name@marketplace）
    Mention { name: String, path: String },
}
```

博客原文总结了这个模式：

> UI 层保留用户意图，core 层负责把意图解释成模型可见上下文和工具集合。

这意味着当用户输入 `@file:src/main.rs fix the bug` 时：
1. TUI 解析出一个 `Mention { kind: File, value: "src/main.rs" }` 和一段 `Text("fix the bug")`
2. Core 收到后，读取文件内容，构造 context fragment，注入到模型请求中
3. 模型看到的是完整的文件内容 + 用户指令，而不是一个 `@file:src/main.rs` 字符串

这种分离的好处是：不同的 client（TUI、VS Code、API）可以构造不同形式的 `UserInput`，但 core 的处理逻辑是统一的。

## 6. App Server：为什么多了一层

博客第 1 篇花了不少篇幅解释为什么 Codex 要在 TUI 和 Core 之间加一层 App Server。核心原因不是"传话"，而是**协议边界**：

```
App Server 的职责：
1. 校验：输入大小、thread 状态、权限
2. 转换：v2 input → core input, turn overrides → TurnContext
3. 路由：按 thread id 分发事件
4. 状态管理：connection state, initialized state
5. 兼容：protocol v2 类型翻译 (camelCase, error mapping)
```

这层的存在意味着：**TUI、VS Code、remote control、其他 client 只要实现 protocol，就可以用同样的 thread/turn 生命周期驱动 core**。

```
传统 CLI：      用户 → 一个进程 → 一个会话
Codex 形态：    多个 client → 连接一个 thread runtime → thread runtime 管理 core session
```

本地 TUI 和远程 client 的差别不是"是否走协议"，而只是"协议跑在进程内还是进程外"。`in_process.rs` 的注释说得很直白：in-process server 保留 app-server 语义，只是去掉进程边界。

## 7. 与 DeepOmni 当前实现的对照

### 7.1 当前状态

DeepOmni 的 Runtime 当前是**同步调用链**模式：

```rust
// crates/deepomni-runtime/src/lib.rs (当前)
impl Runtime {
    pub async fn submit_turn(&self, request: CreateTurnRequest) -> Result<Turn, RuntimeError> {
        // 1. 直接调用 run_turn
        let result = self.inner.turn_runner.run_turn(run_request).await;
        // 2. 同步处理结果
        match result {
            TurnResult::Completed { .. } => { /* 更新状态 */ },
            TurnResult::NeedsApproval { .. } => { /* 写 pending_approvals */ },
        }
        // 3. 返回 Turn
        Ok(turn)
    }
}
```

这和 Codex 的 submission/event 队列对有以下本质差异：

| 维度 | Codex | DeepOmni（当前） |
|------|-------|-------------------|
| 提交方式 | `submit(Op)` 立即返回 SubmissionId | `submit_turn()` 等待 turn 完成才返回 |
| 事件回流 | EventMsg channel, 异步消费 | EventBus broadcast, 但 submit_turn 内部同步 emit |
| Steer 能力 | 有 `steer_input`，用户可中途注入 | 无，必须等 turn 完成 |
| 多 client | 天然支持，都走 Op channel | 不支持，Runtime 方法调用是独占的 |
| Active task 约束 | Session 维护，同一时刻最多一个 | active_turn_id 字段，但无 steer |

### 7.2 差距根因

DeepOmni 的核心问题不在于缺少某个模块，而在于 **Runtime 是一个"同步调用链上的 god object"**：

1. `submit_turn` 方法既构造 TurnContext，又调用 run_turn，又处理结果，又 emit event，又更新 pending_approvals——所有逻辑在一条同步调用链上。
2. `run_turn` 的调用方必须等待它返回，无法在 turn 进行中注入新输入。
3. EventBus 虽然存在，但只是一个"顺便通知"的旁路，不是 core 的唯一出口。

### 7.3 架构升级路径

基于 Codex 的 submission/event 模式，DeepOmni 的升级路径可以分三步走：

**第一步：引入 Op/Event 枚举作为一等类型**

```rust
// 目标：deepomni-protocol/src/ops.rs
pub enum Op {
    UserInput {
        thread_id: ThreadId,
        input: String,
        settings: TurnSettings,
    },
    SteerInput {
        thread_id: ThreadId,
        input: String,
    },
    Approve {
        thread_id: ThreadId,
        approval_id: String,
        decision: ApprovalDecision,
    },
    Reject {
        thread_id: ThreadId,
        approval_id: String,
    },
    Cancel {
        thread_id: ThreadId,
    },
    Compact {
        thread_id: ThreadId,
    },
}
```

**第二步：把 Session 变成后台循环**

```rust
// 目标：deepomni-runtime 内部
struct SessionLoop {
    op_rx: mpsc::UnboundedReceiver<Submission>,
    event_tx: broadcast::Sender<EventMsg>,
    state: SessionState,
    services: Arc<SessionServices>,
}

impl SessionLoop {
    async fn run(&mut self) {
        while let Some(submission) = self.op_rx.recv().await {
            match submission.op {
                Op::UserInput { .. } => self.handle_user_input(submission).await,
                Op::SteerInput { .. } => self.handle_steer(submission).await,
                Op::Approve { .. } => self.handle_approval(submission).await,
                Op::Cancel { .. } => self.handle_cancel(submission).await,
                Op::Compact { .. } => self.handle_compact(submission).await,
                Op::Reject { .. } => self.handle_rejection(submission).await,
            }
        }
    }
}
```

**第三步：Runtime 变成 thin facade**

```rust
// 目标：Runtime 只负责创建 Session、发 Op、订阅 Event
impl Runtime {
    pub fn submit(&self, op: Op) -> SubmissionId {
        let id = SubmissionId::new();
        self.session.op_tx.send(Submission { id, op }).ok();
        id
    }

    pub fn subscribe(&self, thread_id: ThreadId) -> EventSubscriber {
        self.session.event_tx.subscribe()
    }
}
```

这样改完之后：
- `submit_turn` 不再阻塞等待 turn 完成
- Steer 自然支持（发一个 `Op::SteerInput`）
- 多 client 天然支持（都调 `submit`）
- EventBus 成为 core 的唯一出口
- 审批流程也统一为 `Op::Approve` → session loop 处理 → event 回流

## 8. 设计理念总结

### 8.1 Codex 的三个核心设计原则

从博客和源码中提炼出 Codex submission/event 架构的三个核心原则：

**原则一：Core 只通过 Op 接收指令，只通过 Event 发出结果。**

这是整个 harness 架构的基石。Core 不知道谁在调用它（TUI？VS Code？API？remote client？），也不知道谁在消费 event（UI 渲染？持久化？trace？审计？）。这种双向隔离让 core 可以被任意 client 驱动，也可以被任意 observer 观测。

**原则二：用户输入 ≠ 文本字符串。它是 UserInput 类型 + TurnContext 运行时配置。**

Agent 的行为由"用户说了什么"和"在什么环境下说的"共同决定。cwd、权限、沙箱、模型、协作模式等运行时上下文和用户文本一起构成了一个 turn 的完整输入。把它们分开管理（UserInput 保留意图，TurnContext 保留环境），让 core 可以在不同环境下对相同用户输入产生不同行为。

**原则三：一个 Turn 内部可以有多次 model sampling。needs_follow_up 是 agent loop 的心跳。**

工具输出不是终点，而是下一次模型请求的输入。`prompt → model stream → tool call → tool output → next prompt` 这个循环才是 agent 的真正工作单元。Turn 只在模型认为任务完成（返回普通 assistant message，无 follow-up tool call）时才结束。

### 8.2 Claude Code 的三个核心设计原则

**原则一：query() 是一个 async generator，天然适合流式。**

所有输出（模型 delta、工具结果、compaction 事件）都通过 `yield` 流出。调用方用 `for await` 消费。这让 terminal streaming、SDK 输出、headless 处理都可以接在同一个数据流上。

**原则二：工具可以在模型还在流式输出时就开始执行。**

StreamingToolExecutor 实现了边接收边执行的模式。concurrent-safe 工具（如 `list_dir`）可以在模型还在输出下一个工具调用的 JSON 时就开始执行。这对用户感知的延迟有显著改善。

**原则三：应用状态直接进入工具上下文。**

一个 `Tool` 的 `call` 方法可以访问 AppState、UI 渲染函数、MCP client、Agent 状态等运行时信息。这让功能接入路径很短——"我要给工具加一个 UI 提示"只需要在 call 里调 `setToolJSX`。但代价是工具和应用运行时强耦合。

### 8.3 对 DeepOmni 的启示

DeepOmni 的目标是构建一个**可复用的 agent harness**，因此应该更倾向于 Codex 的设计方向：

1. **先建立 Op/Event 边界**：这是从"应用"到"harness"的第一步。没有这个边界，后续的 steer、multi-client、protocol、trace 都无法自然实现。
2. **但从 Claude Code 借鉴流式工具执行**：Codex 的 `ToolCallRuntime` 用 `RwLock` 实现并行，但工具仍然是在一个 turn step 内 batch 执行的。Claude Code 的 `StreamingToolExecutor` 允许边流式边执行，延迟更好。DeepOmni 可以在 Codex 的 Op/Event 边界内，引入 Claude Code 的流式工具执行模式。
3. **UserInput 类型化**：不要把用户输入当作纯字符串传递。定义一个 `UserInput` 枚举（text、image、skill、mention），让不同的 client 可以构造结构化的输入，core 再把它们解释成模型可见上下文。
