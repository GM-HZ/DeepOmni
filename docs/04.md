# 多 Agent 通信、App Server 协议与 Trace

> 引用来源：[Codex 博客第 4 篇：App Server、多 Agent 与 Trace](https://www.wineandchord.com/llm/agent/codex-source-004-appserver/)、[Codex 博客第 5 篇：和 Claude Code 以及行业形态对照](https://www.wineandchord.com/llm/agent/codex-source-005-comparison/)、[Claude Code 源码书](https://sawzhang.github.io/deep-dive-claude-code/index.html)、Codex 源码 `codex-rs/core/src/agent/`、`codex-rs/app-server/src/`、`codex-rs/rollout-trace/src/`、DeepOmni 源码 `crates/deepomni-state/src/lib.rs`、`crates/deepomni-runtime/src/lib.rs`

## 1. 为什么需要多 Agent 和协议层

单个 agent 可以完成简单的编码任务，但复杂的工程场景需要**分治**：

- **并行探索**：搜索代码库的多个目录、同时调研多个方案
- **隔离副作用**：一个 agent 修改文件，另一个 agent 负责测试验证
- **专业化分工**：不同的 agent 有不同的 system prompt 和工具集
- **深度递归**：agent A 发现子问题，spawn agent B 来处理，B 可能再 spawn C

但多 agent 带来了新的工程问题：

1. **通信**：agent 之间如何交换信息？
2. **生命周期**：谁负责创建、监控、回收 agent？
3. **状态隔离**：每个 agent 有自己的历史和上下文，如何避免干扰？
4. **协议边界**：core 和 UI 之间的通信应该走什么接口？
5. **可观测性**：多个 agent 并行工作时，如何知道整体发生了什么？

Codex 和 Claude Code 对这些问题给出了截然不同的解答。Codex 用 **Mailbox + AgentControl + App Server + Rollout Trace** 构建了完整的多 agent 基础设施；Claude Code 用 **forkedAgent + AgentTool** 实现了更轻量的方案。本文将深入分析两者的设计，并与 DeepOmni 当前实现做对照。

## 2. Codex 的多 Agent 架构：Thread-per-Agent

### 2.1 核心模型：一个 Agent = 一个 Thread

Codex 的多 agent 模型建立在一个简洁的等式上：**一个 agent = 一个 CodexThread = 一个 Session**。

当 root agent 需要 spawn 一个子 agent 时，它实际上是创建了一个新的 thread，这个 thread 有自己的：
- `ThreadId`（唯一标识）
- `Session`（独立的 submission/event 队列对）
- `ContextManager`（独立的历史和 token 追踪）
- `TurnContext`（独立的运行时配置快照）
- `Mailbox`（独立的消息收件箱）

博客第 4 篇这样总结：

> 多 agent 不是在一个 session 里跑多个 "角色"，而是真的 spawn 了多个 session。每个 sub-agent 都有自己的 submission queue、event channel、history、tools。parent 和 child 之间的唯一通信管道是 Mailbox。

### 2.2 AgentControl：Agent 的注册中心和生命周期管理器

`AgentControl` 是 Codex 多 agent 系统的核心组件。它在 `core/src/agent/control.rs` 中定义：

```rust
// ref/codex: codex-rs/core/src/agent/control.rs (实际源码)
/// AgentControl 由每个 session 通过 SessionServices 持有。
/// 它提供 spawn 新 agent 和跨 agent 通信的能力。
/// 一个 AgentControl 实例在每个 root thread/session 树中最多创建一次。
/// 同一个 AgentControl 被共享给该 root 下 spawn 的所有 sub-agent，
/// 使得 registry 的作用域限定在该 root thread 而非整个 ThreadManager。
#[derive(Clone, Default)]
pub(crate) struct AgentControl {
    /// 整个 agent control session 共享的 ID
    session_id: SessionId,
    /// 指向全局 thread registry/state 的弱引用
    /// 用 Weak 是为了避免引用循环：
    /// ThreadManagerState -> CodexThread -> Session -> SessionServices -> ThreadManagerState
    manager: Weak<ThreadManagerState>,
    /// Agent 注册表（包含活跃 agent 树、昵称映射等）
    state: Arc<AgentRegistry>,
}
```

`AgentControl` 的核心能力：

**Spawn 新 agent**：

```rust
// ref/codex: control.rs
pub(crate) async fn spawn_agent_with_metadata(
    &self,
    config: Config,
    initial_operation: Op,
    session_source: Option<SessionSource>,
    options: SpawnAgentOptions,
) -> CodexResult<LiveAgent> {
    Box::pin(self.spawn_agent_internal(config, initial_operation, session_source, options)).await
}
```

spawn 流程：
1. 从 `AgentRegistry` 分配一个唯一昵称（从预定义名单中随机选取）
2. 构造 `SessionSource::SubAgent`，标记 depth（递归深度）
3. 通过 `ThreadManagerState` 创建新的 `CodexThread`
4. 新 thread 的 `Session::spawn()` 被调用，创建独立的 submission/event channel
5. 返回 `LiveAgent`（包含 thread_id 和 metadata）

**深度限制**：

```rust
// ref/codex: Session::spawn_internal (实际源码)
if let SessionSource::SubAgent(SubAgentSource::ThreadSpawn { depth, .. }) = session_source
    && depth >= config.agent_max_depth
    && !config.features.enabled(Feature::MultiAgentV2)
{
    // 超过最大深度时，禁用 spawn 能力
    let _ = config.features.disable(Feature::SpawnCsv);
    let _ = config.features.disable(Feature::Collab);
}
```

这是一个重要的安全约束：agent 可以递归 spawn，但深度有上限。超过上限的 agent 失去 spawn 新 agent 的能力，防止无限递归。

### 2.3 AgentRegistry：活跃 Agent 的注册表

```rust
// ref/codex: codex-rs/core/src/agent/registry.rs (实际源码)
/// 为 Codex 的多 agent 能力施加限制：
/// * 限制每个 user session 的 sub-agent 总数
/// 此结构在同一 user session 的所有 agent 之间共享。
#[derive(Default)]
pub(crate) struct AgentRegistry {
    active_agents: Mutex<ActiveAgents>,
    total_count: AtomicUsize,
}

#[derive(Default)]
struct ActiveAgents {
    agent_tree: HashMap<String, AgentMetadata>,
    used_agent_nicknames: HashSet<String>,
    nickname_reset_count: usize,
}

#[derive(Clone, Debug, Default)]
pub(crate) struct AgentMetadata {
    pub(crate) agent_id: Option<ThreadId>,
    pub(crate) agent_path: Option<AgentPath>,
    pub(crate) agent_nickname: Option<String>,
    pub(crate) agent_role: Option<String>,
    pub(crate) last_task_message: Option<String>,
}
```

`AgentRegistry` 的职责：
1. **追踪活跃 agent**：维护 `agent_tree`（agent path → metadata 映射）
2. **昵称分配**：从预定义列表中分配不重复的昵称（如 "atlas"、"spark"）
3. **总数限制**：通过 `total_count` 限制每个 session 的 agent 总数
4. **状态查询**：列出所有活跃 agent 及其状态

### 2.4 AgentPath：树状寻址

Codex 用 `AgentPath` 来标识 agent 在树中的位置：

```
/root                     ← root agent
/root/atlas               ← root 的第一个子 agent
/root/atlas/spark         ← atlas 的子 agent
/root/nova                ← root 的第二个子 agent
```

`AgentPath` 是一个字符串路径，类似文件系统路径。它的作用是：
1. **唯一标识**：每个 agent 在树中有唯一的路径
2. **父子关系**：通过路径前缀判断父子关系
3. **消息路由**：`InterAgentCommunication` 的 `author` 和 `recipient` 字段用的就是 `AgentPath`

### 2.5 SpawnAgentForkMode：历史共享策略

当 parent spawn child 时，child 需要一些初始上下文。Codex 提供了两种模式：

```rust
// ref/codex: control.rs
pub(crate) enum SpawnAgentForkMode {
    /// child 继承 parent 的完整历史
    FullHistory,
    /// child 只继承 parent 最近 N 个 turn 的历史
    LastNTurns(usize),
}
```

`LastNTurns` 是推荐模式——child 不需要知道 parent 从一开始的所有对话，只需要最近几轮的上下文就够了。这大幅减少了 child 的初始 token 消耗。

## 3. Mailbox：Agent 间的通信管道

### 3.1 设计：mpsc channel + sequence number

`Mailbox` 是 Codex 的跨 agent 通信原语：

```rust
// ref/codex: codex-rs/core/src/agent/mailbox.rs (完整实际源码)
pub(crate) struct Mailbox {
    /// 发送端（unbounded mpsc channel）
    tx: mpsc::UnboundedSender<InterAgentCommunication>,
    /// 全局递增序列号
    next_seq: AtomicU64,
    /// watch channel，通知接收方"有新邮件"
    seq_tx: watch::Sender<u64>,
}

pub(crate) struct MailboxReceiver {
    /// 接收端
    rx: mpsc::UnboundedReceiver<InterAgentCommunication>,
    /// 本地缓冲队列（try_recv 后暂存）
    pending_mails: VecDeque<InterAgentCommunication>,
}

impl Mailbox {
    pub(crate) fn new() -> (Self, MailboxReceiver) {
        let (tx, rx) = mpsc::unbounded_channel();
        let (seq_tx, _) = watch::channel(0);
        (
            Self { tx, next_seq: AtomicU64::new(0), seq_tx },
            MailboxReceiver { rx, pending_mails: VecDeque::new() },
        )
    }

    /// 订阅序列号变化（用于 select! 等待新邮件到达）
    pub(crate) fn subscribe(&self) -> watch::Receiver<u64> {
        self.seq_tx.subscribe()
    }

    /// 发送消息，返回分配的序列号
    pub(crate) fn send(&self, communication: InterAgentCommunication) -> u64 {
        let seq = self.next_seq.fetch_add(1, Ordering::Relaxed) + 1;
        let _ = self.tx.send(communication);
        self.seq_tx.send_replace(seq);
        seq
    }
}

impl MailboxReceiver {
    /// 从 channel 同步所有待处理消息到本地 pending_mails
    fn sync_pending_mails(&mut self) {
        while let Ok(mail) = self.rx.try_recv() {
            self.pending_mails.push_back(mail);
        }
    }

    /// 是否有待处理消息
    pub(crate) fn has_pending(&mut self) -> bool {
        self.sync_pending_mails();
        !self.pending_mails.is_empty()
    }

    /// 是否有需要触发新 turn 的消息
    pub(crate) fn has_pending_trigger_turn(&mut self) -> bool {
        self.sync_pending_mails();
        self.pending_mails.iter().any(|mail| mail.trigger_turn)
    }

    /// 排空所有待处理消息
    pub(crate) fn drain(&mut self) -> Vec<InterAgentCommunication> {
        self.sync_pending_mails();
        self.pending_mails.drain(..).collect()
    }
}
```

### 3.2 InterAgentCommunication：消息体

```rust
// ref/codex: codex-rs/protocol/src/protocol.rs (实际源码)
pub struct InterAgentCommunication {
    /// 消息发送者的 AgentPath
    pub author: AgentPath,
    /// 主接收者的 AgentPath
    pub recipient: AgentPath,
    /// 其他接收者（广播场景）
    #[serde(default)]
    pub other_recipients: Vec<AgentPath>,
    /// 消息内容（纯文本）
    pub content: String,
    /// 是否触发接收方启动新的 turn
    pub trigger_turn: bool,
}
```

`trigger_turn` 是一个非常巧妙的设计：当 child agent 完成任务后，它发送一条 `trigger_turn: true` 的消息给 parent。parent 的 session loop 在 `select!` 中同时等待用户输入和 mailbox 消息。收到 `trigger_turn` 消息后，parent 会自动开始一个新的 turn 来处理 child 的结果——不需要用户手动触发。

### 3.3 消息的生命周期

```
1. parent 调用 spawn_agent_with_metadata()
   → child thread 被创建，获得自己的 Mailbox
   
2. parent 通过 Op::InterAgentCommunication 发送初始指令给 child
   → child.mailbox.send(communication)
   → child 的 session loop 在下一轮 select! 中收到消息
   
3. child 执行任务，产生结果

4. child 通过 InterAgentCommunication 发送结果给 parent
   → parent.mailbox.send(result_communication)
   → trigger_turn: true → parent 自动开始新 turn

5. parent 在新 turn 中处理 child 的结果
   → drain mailbox → 将消息内容注入历史 → 模型看到 child 的输出
```

### 3.4 Op::InterAgentCommunication：通过 Submission 队列传递

跨 agent 消息不是直接塞进对方的历史——它走 `Op` 通道：

```rust

    /// 中断当前任务，不终止后台终端进程

    /// 开始实时对话流

    /// 发送音频输入到实时对话流

        environments: Option<Vec<TurnEnvironmentSelection>>,

        responsesapi_client_metadata: Option<HashMap<String, String>>,
    },
    /// 带 turn context 覆盖的用户输入（保持提交顺序，覆盖被拒绝时输入不会启动）
    UserInputWithTurnContext {
        items: Vec<UserInput>,
        environments: Option<Vec<TurnEnvironmentSelection>>,
        final_output_json_schema: Option<Value>,
        responsesapi_client_metadata: Option<HashMap<String, String>>,
        cwd: Option<PathBuf>,
        approval_policy: Option<AskForApproval>,
        approvals_reviewer: Option<ApprovalsReviewer>,
        sandbox_policy: Option<SandboxPolicy>,
        permission_profile: Option<PermissionProfile>,
        active_permission_profile: Option<ActivePermissionProfile>,
        windows_sandbox_level: Option<WindowsSandboxLevel>,
        model: Option<String>,
        effort: Option<Option<ReasoningEffortConfig>>,
        summary: Option<ReasoningSummaryConfig>,
        service_tier: Option<Option<String>>,
        collaboration_mode: Option<CollaborationMode>,
        personality: Option<Personality>,
    },
    /// CodexThread 所需的完整 turn 上下文
    UserTurn {
        items: Vec<UserInput>,
        cwd: PathBuf,
        approval_policy: AskForApproval,
        approvals_reviewer: Option<ApprovalsReviewer>,
        sandbox_policy: SandboxPolicy,
        permission_profile: Option<PermissionProfile>,
        model: String,
        effort: Option<ReasoningEffortConfig>,

        final_output_json_schema: Option<Value>,
        collaboration_mode: Option<CollaborationMode>,
        personality: Option<Personality>,
        environments: Option<Vec<TurnEnvironmentSelection>>,
    },
    /// 跨 agent 通信，作为 assistant 历史记录
    InterAgentCommunication {
        communication: InterAgentCommunication,
    },
    /// 覆盖后续 turn 的持久化 turn context 的部分字段

```

这意味着跨 agent 消息和用户输入走同一条路径——都是 Op，都进 submission queue，都由 session loop 处理。这保证了消息的有序性和一致性。

## 4. Claude Code 的多 Agent：forkedAgent + AgentTool

### 4.1 设计理念：Fork 而非 Spawn

Claude Code 的多 agent 模型和 Codex 完全不同。它不创建独立的 session，而是**fork 当前 query loop**：

```typescript
// ref/claude-code: src/utils/forkedAgent.ts (实际源码注释)
/**
 * Helper for running forked agent query loops with usage tracking.
 *
 * This utility ensures forked agents:
 * 1. Share identical cache-critical params with the parent to guarantee prompt cache hits
 * 2. Track full usage metrics across the entire query loop
 * 3. Log metrics via the tengu_fork_agent_query event when complete
 * 4. Isolate mutable state to prevent interference with the main agent loop
 */
```

关键设计：

**Cache-safe forking**：fork 的 agent 必须和 parent 共享相同的 `CacheSafeParams`（system prompt、tools、model、messages prefix），这样 Anthropic API 可以复用 parent 的 prompt cache。

```typescript
// ref/claude-code: src/utils/forkedAgent.ts (实际源码)
export type CacheSafeParams = {
    /** System prompt - must match parent for cache hits */
    systemPrompt: SystemPrompt
    /** User context - prepended to messages, affects cache */
    userContext: string
    /** System context - appended to system prompt, affects cache */
    systemContext: string
    /** Tool definitions and settings */
    toolUseContext: ToolUseContext
    /** Messages used for fork context */
    forkContextMessages: Message[]
}
```

**Mutable state isolation**：每个 fork 有自己的 mutable state（messages、file state cache、content replacement state），但共享 parent 的 immutable config。

### 4.2 AgentTool：模型驱动的 Agent Spawn

Claude Code 的 `AgentTool`（在 `src/tools/AgentTool/runAgent.ts`）是模型调用的一个工具。当模型认为需要并行探索或子任务委派时，它调用 `AgentTool`：

```typescript
// ref/claude-code: src/tools/AgentTool/runAgent.ts (实际源码头部)
import { query } from '../../query.js'
import { createSubagentContext } from '../../utils/forkedAgent.js'
import { getAgentModel } from '../../utils/model/agent.js'
import { createUserMessage } from '../../utils/messages.js'
import { killShellTasksForAgent } from '../../tasks/LocalShellTask/killShellTasks.js'
import { clearAgentTranscriptSubdir, recordSidechainTranscript } from '../../utils/sessionStorage.js'
import { cleanupAgentTracking } from '../../services/api/promptCacheBreakDetection.js'

// AgentTool 的核心流程：
// 1. 通过 createSubagentContext() 从 parent 的 toolUseContext 创建 subagent context
//    → 内部调用 cloneFileStateCache() 隔离 mutable state
//    → 保留 parent 的 CacheSafeParams（systemPrompt、tools、model、messages prefix）
// 2. 用 createUserMessage() 构造 subagent 的初始 messages（parent 上下文 + 子任务指令）
// 3. 用 getAgentModel() 获取 subagent 模型（可能和 parent 不同）
// 4. 调用 query() 启动独立的 query loop，通过 yield 流式回传进度
// 5. query loop 结束后，调用 killShellTasksForAgent() 清理后台 shell
// 6. 调用 cleanupAgentTracking() 清理 prompt cache 追踪
// 7. 调用 recordSidechainTranscript() 保存 subagent 对话记录
// 8. 返回 subagent 的最终输出作为 tool result 给 parent
```

### 4.3 Codex vs Claude Code 多 Agent 对比

| 维度 | Codex | Claude Code |
|------|-------|-------------|
| **隔离级别** | Thread 级（独立 session、独立 event channel） | Query loop 级（独立 messages，共享 config） |
| **通信方式** | Mailbox（mpsc channel + InterAgentCommunication） | 返回值（tool result 回传给 parent） |
| **异步性** | 真正异步——parent 和 child 可以并行执行 | 同步——parent 等待 child query loop 完成 |
| **生命周期** | 独立——child 可以在 parent 结束后继续存活 | 嵌套——child 的 query loop 结束后就消失 |
| **深度限制** | `agent_max_depth` 配置 | 无显式限制（但受 context window 约束） |
| **状态持久化** | child 有自己的 thread（可持久化到 rollout） | 无持久化（fork 结束后 state 丢弃） |
| **Cache 优化** | 无特殊优化 | CacheSafeParams 保证 prompt cache 复用 |
| **昵称系统** | AgentRegistry 分配唯一昵称 | AgentId（UUID） |
| **进度可见性** | 通过 EventMsg 流式回传 | 通过 yield 流式回传 |

Codex 的方案更适合**长时间运行的并行任务**（如"一个 agent 搜索，一个 agent 编辑，一个 agent 测试"），Claude Code 的方案更适合**短时间的子任务委派**（如"让一个 agent 读取这几个文件并总结"）。

## 5. App Server：协议边界层

### 5.1 Codex 的 App Server：为什么要多一层

博客第 4 篇花了大量篇幅解释 App Server 的必要性。核心原因不是"传话"，而是**协议边界**：

```
传统 CLI：      用户 → 一个进程 → 一个会话
Codex 形态：    多个 client → App Server → Core Session(s)
```

App Server 的五大职责：

1. **校验**：输入大小、thread 状态、权限检查
2. **转换**：v2 protocol 类型 ↔ core 内部类型（camelCase ↔ snake_case）
3. **路由**：按 thread id 分发事件到正确的 connection
4. **状态管理**：connection state、initialized state、thread watch
5. **兼容**：protocol v2 类型翻译、error mapping

### 5.2 In-Process Server：去掉进程边界

Codex 的 `in_process.rs` 模块实现了**进程内 App Server**：

```rust
// ref/codex: codex-rs/app-server/src/in_process.rs (实际源码注释)
//! In-process app-server runtime host for local embedders.
//!
//! This module runs the existing MessageProcessor and outbound routing logic
//! on Tokio tasks, but replaces socket/stdio transports with bounded in-memory
//! channels. The intent is to preserve app-server semantics while avoiding a
//! process boundary for CLI surfaces that run in the same process.
```

这意味着本地 TUI 和远程 client 的差别不是"是否走协议"，而只是"协议跑在进程内还是进程外"。`in_process.rs` 的注释说得很直白：保留 app-server 语义，只是去掉进程边界。

### 5.3 Bespoke Event Handling：事件翻译层

`bespoke_event_handling.rs` 是 App Server 最复杂的模块之一。它负责把 core 的 `EventMsg` 翻译成 App Server protocol 的类型。它的 import 列表就说明了复杂度：

## 6. Rollout Trace：诊断图谱

### 6.1 Codex 的 Rollout Trace 系统

Codex 博客第 4 篇用了一个精辟的比喻：**"observe first, interpret later"**。Rollout trace 不是 log，不是 metrics，而是一种**结构化的事件图谱**，记录了一次完整 rollout（从用户输入到 agent 完成）中发生的所有事件。

```rust
// ref/codex: codex-rs/rollout-trace/src/lib.rs (实际源码注释)
//! Trace bundle format, writer, and reducer for Codex rollouts.
//!
//! This crate owns the trace schema. Hot-path Codex code should depend on the
//! small writer API here; semantic replay and viewer projections stay outside
//! `codex-core`.
```

设计原则：
1. **Hot path 只写不读**：core 代码只调用 writer API 追加事件，不做分析
2. **Semantic replay 在外部**：`reducer` 模块把原始事件还原成结构化的 `RolloutTrace`
3. **Viewer 和 core 解耦**：trace 的可视化、查询都在 core 之外

### 6.2 Trace 的层次结构

Rollout trace 是一个树状结构：

```
RolloutBundle（一次完整的 rollout）
  └── ThreadTraceContext（每个 thread/agent 一个）
        ├── ThreadStartedTraceMetadata（thread 启动元数据）
        ├── CodexTurnId → turn events（每个 turn 的事件）
        │     ├── InferenceTraceContext（模型推理追踪）
        │     │     └── InferenceTraceAttempt（每次推理尝试）
        │     ├── ToolDispatchTraceContext（工具执行追踪）
        │     │     └── ToolDispatchInvocation（每次工具调用）
        │     ├── CompactionTraceContext（压缩追踪）
        │     │     └── CompactionCheckpointTracePayload（压缩检查点）
        │     └── CodeCellTraceContext（代码执行追踪）
        └── AgentResultTracePayload（child agent 完成通知）
```

### 6.4 Trace 的 No-Op 模式

`ThreadTraceContext` 支持 no-op 模式——当 `CODEX_ROLLOUT_TRACE_ROOT` 环境变量未设置时，所有 `record_*` 方法都是空操作。这意味着 trace 的性能开销在未启用时为零。

```rust
// ref/codex: rollout-trace/src/thread.rs (实际源码)
#[derive(Clone, Debug)]
enum ThreadTraceContextState {
    Disabled,
    Enabled(EnabledThreadTraceContext),
}

#[derive(Clone, Debug)]
struct EnabledThreadTraceContext {
    /// 共享的 trace writer（append-only 写入 trace.jsonl）
    writer: Arc<TraceWriter>,
    /// 根 thread 的 ID（整个 rollout bundle 共用）
    root_thread_id: AgentThreadId,
    /// 当前 thread 的 ID
    thread_id: AgentThreadId,
}

impl ThreadTraceContext {
    /// 构建一个不记录任何事件的 no-op 句柄
    pub fn disabled() -> Self {
        Self { state: ThreadTraceContextState::Disabled }
    }

    /// 从环境变量 CODEX_ROLLOUT_TRACE_ROOT 启动 root thread trace
    /// trace 启动是 best-effort 的：失败不会导致 Codex session 不可用
    pub fn start_root_or_disabled(metadata: ThreadStartedTraceMetadata) -> Self {
        let Some(root) = std::env::var_os(CODEX_ROLLOUT_TRACE_ROOT_ENV) else {
            return Self::disabled();
        };
        let root = PathBuf::from(root);
        match start_root_in_root(root.as_path(), metadata) {
            Ok(context) => context,
            Err(err) => {
                warn!("failed to initialize rollout trace bundle: {err:#}");
                Self::disabled()
            }
        }
    }

    /// 在已有的 rollout bundle 内启动一个子 thread 的 trace
    pub(crate) fn start(
        writer: Arc<TraceWriter>,
        root_thread_id: AgentThreadId,
        metadata: ThreadStartedTraceMetadata,
    ) -> Self {
        let context = EnabledThreadTraceContext {
            writer,
            root_thread_id,
            thread_id: metadata.thread_id.clone(),
        };
        record_thread_started(&context, metadata);
        Self { state: ThreadTraceContextState::Enabled(context) }
    }

    /// 当前句柄是否会写入 trace 事件
    pub fn is_enabled(&self) -> bool {
        matches!(self.state, ThreadTraceContextState::Enabled(_))
    }
}
```

### 6.5 Reduced State：从原始事件到结构化模型

`rollout-trace` 的 `reducer` 模块负责把原始的 `trace.jsonl`（append-only 事件流）还原成结构化的 `RolloutTrace`：

```
trace.jsonl（原始事件）
    → replay_bundle()（reducer 函数）
        → RolloutTrace（结构化模型）
            → state.json（缓存在 bundle 目录旁边）
```

这种"先写后读"的模式有一个重要好处：**原始事件永远不会被修改**。即使 reducer 的逻辑发生变化（比如想提取新的指标），也可以重新 replay 原始事件来生成新的 reduced state。

### 6.6 Claude Code 的 Trace 方案

Claude Code 的追踪更简单：

1. **logEvent**：关键事件通过 `logEvent()` 发送到 analytics（如 `tengu_auto_compact_succeeded`、`tengu_fork_agent_query`）
2. **Transcript**：通过 `recordSidechainTranscript()` 把 agent 的对话记录保存到本地文件
3. **Perfetto**：实验性的 Perfetto tracing 支持（通过 `isPerfettoTracingEnabled()`）

与 Codex 的差异：Claude Code 的 trace 是**事件驱动**的（发生了什么就 log 什么），Codex 的 trace 是**结构驱动**的（先定义 schema，再往 schema 里填事件）。Codex 的方案更适合后期分析（"replay 这个 rollout 的所有 inference"），Claude Code 的方案更适合实时监控（"这个 compact 成功了吗"）。

## 9. 设计理念总结

### 9.1 Codex 的三个核心原则

**原则一：Agent = Thread。一个 agent 就是一个独立的 session，有自己的 context、tools、event channel。**

这保证了隔离性——一个 agent 的 compaction 不会影响另一个 agent 的历史。但代价是 spawn 一个 agent 的开销不小（创建 session、加载 config、初始化 tools）。

**原则二：通信通过 Mailbox，不通过共享内存。**

Codex 的 agent 之间不共享任何 mutable state。所有信息交换都通过 `InterAgentCommunication` 消息。这是一种 actor model 的变体——每个 agent 是一个 actor，Mailbox 是 actor 的 inbox。

**原则三：App Server 是协议边界，不是传话人。**

App Server 做校验、转换、路由、状态管理。它把"能连上 core 的 client"从"知道 core 内部实现的 client"中区分出来。任何实现了 protocol 的 client 都可以驱动 core，不需要知道 core 用的是什么语言、什么 model provider。

### 9.2 Claude Code 的三个核心原则

**原则一：Fork 而非 Spawn。子 agent 是 parent query loop 的一个分支。**

Claude Code 的 agent 不是独立进程/session，而是当前 query loop 的一个递归调用。这让 spawn 开销极小（构造一个新的 messages 数组 + 调用 `query()`），但缺点是 child 的生命周期严格依附于 parent——parent 取消，child 也取消。

**原则二：Cache-safe 是多 agent 的第一约束。**

Claude Code 的 `CacheSafeParams` 确保 fork 的 agent 和 parent 共享 prompt cache。这是一个性能优化——如果每个 fork 都要重新填充 cache，多 agent 的延迟和成本会翻倍。

**原则三：隐式协议，显式 analytics。**

Claude Code 不定义显式的协议类型——`query()` 的 `yield` 就是协议。但它在关键路径上有丰富的 analytics（`logEvent`），让团队可以追踪性能和质量指标。

### 9.3 对 DeepOmni 的启示

DeepOmni 的目标是构建可复用的 agent harness，因此在多 Agent 和协议层面应该更倾向于 Codex 的方向：

1. **优先实现 Mailbox 和 AgentControl**：这是多 Agent 的基础。没有通信管道和生命周期管理，多 Agent 只是"多个独立的 session"，无法协作。

2. **在 server 和 runtime 之间引入协议翻译层**：当前 server 直接调用 runtime 方法，这意味着每个新的 client 类型（Web、VS Code、API）都要重复实现一遍调用逻辑。引入 ProtocolAdapter 后，所有 client 只需要实现 protocol，调用逻辑集中在一处。

3. **Trace 系统用 trait + no-op 模式**：不是所有场景都需要 trace。定义 `TraceWriter` trait 后，生产环境可以用 SQLite writer，开发环境可以用 no-op，诊断模式可以用 bundle writer。

4. **从 Claude Code 借鉴 cache-safe forking**：Codex 的 Thread-per-Agent 模型隔离性好但开销大。对于轻量级子任务（如"读取这几个文件并总结"），可以引入 Claude Code 式的 fork 模式——不创建新 session，只 fork 当前的 messages 和 context_manager。
