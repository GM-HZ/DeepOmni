# 上下文工程——状态系统、记忆与压缩

> 引用来源：[Codex 博客第 3 篇：上下文、记忆与压缩](https://www.wineandchord.com/llm/agent/codex-source-003-context/)、[Claude Code 源码书](https://sawzhang.github.io/deep-dive-claude-code/index.html)、Codex 源码 `codex-rs/core/src/context_manager/`、`codex-rs/core/src/compact.rs`、DeepOmni 源码 `crates/deepomni-context/src/lib.rs`

---

## 1. 为什么上下文工程是 Agent 的核心战场

一个 coding agent 的真正瓶颈不是"能不能调模型"，而是**给模型看什么**。模型的 context window 是有限的（128K–200K tokens），但一个真实的编码会话可以产生远超窗口的历史：用户消息、助手回复、工具调用、工具输出（一个 `cat` 命令的输出可能就 10K tokens）、reasoning traces、文件内容注入、skill 指令、plugin 描述……

上下文工程要回答的核心问题是：

1. **What to keep**：哪些历史项对下一次模型请求有价值？
2. **What to drop**：哪些可以安全丢弃而不影响模型决策质量？
3. **How to compress**：当窗口不够时，如何把历史压缩成更紧凑的形式？
4. **When to compress**：什么时候触发压缩，手动还是自动？
5. **How to recover**：压缩后如果模型质量下降，能否回滚？

Codex 博客第 3 篇把这个问题总结为三个关键词：**Context Fragment**（内容的结构化载体）、**ContextManager**（历史的 token-aware 管理器）、**Compaction**（模型驱动的摘要替换）。Claude Code 则用 `AutoCompactTracker` + `query loop 内的 compaction 检测` 来处理同样的问题。

本文将深入分析这三个系统在 Codex、Claude Code 和 DeepOmni 中的实现，揭示它们的设计理念差异，并给出 DeepOmni 的升级路径。

## 2. Context Fragment：内容的结构化载体

### 2.1 Codex 的 ContextualUserFragment trait

Codex 的上下文注入不是"把字符串拼到 prompt 里"。它定义了一个 trait `ContextualUserFragment`，每个 fragment 都有：

```rust
// ref/codex: codex-rs/core/src/context/fragment.rs
pub trait ContextualUserFragment {
    /// 这个 fragment 在 API 请求中的角色（user / developer / system）
    const ROLE: &'static str;
    /// XML-like 开始标记，用于后续识别和过滤
    const START_MARKER: &'static str;
    /// XML-like 结束标记
    const END_MARKER: &'static str;

    /// fragment 的主体内容
    fn body(&self) -> String;

    /// 检查一段文本是否匹配这个 fragment 的标记
    fn matches_text(text: &str) -> bool
    where
        Self: Sized,
    {
        if Self::START_MARKER.is_empty() || Self::END_MARKER.is_empty() {
            return false;
        }
        let trimmed = text.trim_start();
        let starts_with_marker = trimmed
            .get(..Self::START_MARKER.len())
            .is_some_and(|c| c.eq_ignore_ascii_case(Self::START_MARKER));
        let trimmed = trimmed.trim_end();
        let ends_with_marker = trimmed
            .get(trimmed.len().saturating_sub(Self::END_MARKER.len())..)
            .is_some_and(|c| c.eq_ignore_ascii_case(Self::END_MARKER));
        starts_with_marker && ends_with_marker
    }

    /// 渲染：标记 + 主体 + 标记
    fn render(&self) -> String {
        if Self::START_MARKER.is_empty() && Self::END_MARKER.is_empty() {
            return self.body();
        }
        format!("{}{}{}", Self::START_MARKER, self.body(), Self::END_MARKER)
    }

    /// 转成 ResponseItem（API 请求中的一个 item）
    fn into(self) -> ResponseItem
    where
        Self: Sized,
    {
        ResponseItem::Message {
            id: None,
            role: Self::ROLE.to_string(),
            content: vec![ContentItem::InputText { text: self.render() }],
            phase: None,
        }
    }
}
```

这个设计有几个非常精妙的点：

**第一，标记化（Marked Fragments）**。每个 fragment 用 XML-like 的 `START_MARKER` / `END_MARKER` 包裹主体内容。这不是为了让模型解析 XML——模型不需要知道这些标记的存在。标记的作用是让 **compaction 和 filtering 代码** 能在历史中识别出"这段内容是一个 skill 指令"或"这段内容是环境信息"。

博客原文这样解释：

> 这些 marker/tag 不是给模型看的（模型不需要解析 XML），而是给 context filtering 代码用的。当 compaction 发生时，filtering code 需要知道"这段内容是一个 skill 指令吗？还是用户真正说的话？"如果是 skill 指令，compaction 可以安全地把它标记为"可重新注入"而不是"必须保留原文"。

**第二，角色分离**。每个 fragment 都声明自己的 `ROLE`。大部分上下文注入都用 `developer` 角色——这在 OpenAI API 中介于 `system` 和 `user` 之间，模型把它当作"开发者提供的背景信息"处理。这比一股脑塞进 system prompt 要好：system prompt 是全局固定的，developer messages 可以按 turn 动态注入。

**第三，FragmentRegistration 类型擦除**。Codex 还提供了 `FragmentRegistration` trait 和 `FragmentRegistrationProxy<T>`，用于在不构造具体 fragment 实例的情况下检查历史文本是否匹配某个 fragment 类型。这是一个典型的编译期多态 + 运行时查询的模式。

Codex 的 `context/` 目录下有大量具体 fragment 实现：

| Fragment | 角色 | 用途 |
|----------|------|------|
| `user_instructions.rs` | developer | AGENTS.md / 用户自定义指令 |
| `skill_instructions.rs` | developer | 已激活 skill 的 SKILL.md 内容 |
| `plugin_instructions.rs` | developer | 插件能力描述 |
| `environment_context.rs` | developer | 工作区环境信息（git、cwd、OS） |
| `permissions_instructions.rs` | developer | 当前权限配置说明 |
| `collaboration_mode_instructions.rs` | developer | 协作模式（proactive/reactive/...） |
| `personality_spec_instructions.rs` | developer | personality 偏好 |
| `approved_command_prefix_saved.rs` | developer | 已批准的命令前缀 |
| `network_rule_saved.rs` | developer | 已保存的网络规则 |
| `subagent_notification.rs` | developer | 子 agent 通知 |
| `turn_aborted.rs` | developer | turn 中止提示 |
| `guardian_followup_review_reminder.rs` | developer | Guardian 审查提醒 |

### 2.2 Claude Code 的 developer message 注入

Claude Code 没有 `ContextualUserFragment` 这样的 trait 抽象，但它有一套等价的模式：**developer message 注入**。

在 `query.ts` 的每一轮循环开始前，Claude Code 会构造一批 developer messages，插入到 conversation history 的适当位置：

```typescript
// ref/claude-code: src/query.ts (实际源码 queryLoop 函数)
// Claude Code 在 query loop 的每一轮开始时，把 systemPrompt + systemContext
// 拼成 fullSystemPrompt，然后通过 appendSystemContext 注入上下文：
const fullSystemPrompt = asSystemPrompt(
    appendSystemContext(systemPrompt, systemContext),
)

// systemContext 包含环境信息、工具列表、自定义指令等，
// 由 QueryEngine 在 query 调用前构造。
// userContext 则在 API 调用时作为独立参数传递。
// 这两者都不进入持久化的 messages 数组。
```

Claude Code 和 Codex 的关键区别在于：

1. **Codex 的 fragment 是持久化到历史中的**。它们作为 `ResponseItem::Message` 被 `record_items` 到 `ContextManager` 里，后续 turn 可以看到、compaction 可以识别和过滤。
2. **Claude Code 的 developer messages 是每轮临时构造的**。它们不进入持久化历史，每轮都重新生成。这意味着 Claude Code 的上下文注入更"无状态"——但也意味着当 compaction 发生时，压缩后的历史里不包含这些上下文，下一轮需要重新注入。

### 2.3 DeepOmni 的 ContextFragment 枚举

DeepOmni 的 `ContextFragment` 是一个枚举，设计上结合了 Codex 的标记化和 Claude Code 的分类：

```rust
// crates/deepomni-context/src/lib.rs
pub enum ContextFragment {
    /// 系统提示（始终包含，永不丢弃）
    System { content: String },
    /// 工具 schema 描述
    ToolSchemas { content: String },
    /// 已激活 skill 的指令
    SkillInstruction { skill_name: String, content: String },
    /// 插件能力摘要
    PluginCapability { plugin_id: String, content: String },
    /// 对话消息
    ConversationMessage { role: String, content: String, message_id: Option<MessageId> },
    /// 工具调用结果（待续材料——永不丢弃）
    ToolResult { call_id: String, content: String },
    /// 推理内容（replay 需要——永不丢弃）
    ReasoningReplay { message_id: MessageId, content: String },
    /// 环境信息（工作区、git 等）
    Environment { content: String },
}
```

DeepOmni 的 `ContextFragment` 提供了三个关键方法：

1. **`marker_tag()`**：返回 fragment 的标记标签（如 `"tool-schemas"`、`"skill-instruction"`），用于 compaction 时识别和过滤。这直接借鉴了 Codex 的 `START_MARKER` / `END_MARKER` 模式。
2. **`is_protected()`**：标记哪些 fragment 是"永不丢弃"的。System prompt、ToolResult、ReasoningReplay 是受保护的。
3. **`estimated_tokens()`**：粗略估算 token 数（字符数 ÷ 4），用于 budget 决策。

与 Codex 的差异：
- Codex 用 **trait 多态**（每种 fragment 是一个独立的 struct 实现 trait），适合大型代码库的扩展性。
- DeepOmni 用 **枚举**（所有 fragment 类型在一个 enum 里），更紧凑但扩展性稍差。
- Codex 的 `FragmentRegistration` 允许在不构造实例的情况下做类型匹配，DeepOmni 尚无等价机制。

## 3. ContextManager：历史的 Token-Aware 管理器

### 3.1 Codex 的 ContextManager：生产级复杂度

Codex 的 `ContextManager`（定义在 `core/src/context_manager/history.rs`）是整个 agent 的**记忆中枢**。它不只是一个 `Vec<ResponseItem>`，而是一个带有 token 追踪、版本控制、normalization、rollback 能力的完整状态机。

核心字段：

```rust
// ref/codex: codex-rs/core/src/context_manager/history.rs
pub(crate) struct ContextManager {
    /// 历史项，从最旧到最新排列
    items: Vec<ResponseItem>,
    /// 每次历史重写时递增（compaction、rollback 等）
    history_version: u64,
    /// 上一次 API 响应的 token 使用信息
    token_info: Option<TokenUsageInfo>,
    /// 参考上下文快照，用于 diffing 和生成 model-visible 的设置更新项
    reference_context_item: Option<TurnContextItem>,
}
```

关键能力矩阵：

| 能力 | 方法 | 说明 |
|------|------|------|
| **记录** | `record_items()` | 追加历史项，同时应用 truncation policy |
| **构造 prompt** | `for_prompt()` | 返回 normalization 后的历史，消费 self |
| **版本追踪** | `history_version()` | 每次重写递增，用于检测历史是否被修改 |
| **token 估算** | `estimate_token_count()` | 基于字节的粗略 token 估算 |
| **token 追踪** | `get_total_token_usage()` | 结合 API 返回的 usage 和本地新增项估算 |
| **token breakdown** | `get_total_token_usage_breakdown()` | 返回 API 侧 tokens + 本地新增 tokens 的分解 |
| **替换历史** | `replace()` | 用新项替换全部历史（compaction 后使用） |
| **删除最旧项** | `remove_first_item()` | 删除最早的 item（context window exceeded 时使用） |
| **删除最新项** | `remove_last_item()` | 删除最后的 item（rollback 时使用） |
| **rollback** | `drop_last_n_user_turns()` | 按 turn 边界回退指定数量的 turn |
| **图片替换** | `replace_last_turn_images()` | 用占位文本替换上一轮的工具输出图片 |
| **normalization** | `normalize_history()` | 确保 call/output 配对、去除孤立 output、剥离不支持的图片 |

最值得注意的是 **normalization 三步曲**：

```rust
// ref/codex: context_manager/history.rs
fn normalize_history(&mut self, input_modalities: &[InputModality]) {
    // 1. 每个 function/tool call 必须有对应的 output
    normalize::ensure_call_outputs_present(&mut self.items);
    // 2. 每个 output 必须有对应的 call
    normalize::remove_orphan_outputs(&mut self.items);
    // 3. 模型不支持图片时，从 messages 和 tool outputs 中剥离图片
    normalize::strip_images_when_unsupported(input_modalities, &mut self.items);
}
```

这个 normalization 在每次 `for_prompt()` 调用时执行。它的存在是因为：compaction 可能删除了一个 tool call 但保留了它的 output，或者反过来。如果不做 normalization，模型 API 会拒绝请求（`function_call_output without corresponding function_call`）。

博客原文对此的评价：

> ContextManager 不仅是"历史数组"，它是一个 token-aware 的状态机。每次 compaction/rollback/truncation 之后，normalization 确保历史的结构完整性。

### 3.2 Token 追踪的双层策略

Codex 的 token 追踪采用了一个巧妙的**双层策略**：

**第一层：API 响应中的 usage**。每次模型 API 返回时，response 里包含 `usage.total_tokens`。这是服务器端真实的 token 计数。`update_token_info()` 把它存到 `token_info` 里。

**第二层：本地新增项的估算**。在两次 API 调用之间，用户可能又输入了新消息、工具又产生了新输出。这些新增项的 token 数不在上一次 API 响应的 `total_tokens` 里。`get_total_token_usage()` 通过 `items_after_last_model_generated_item()` 找出"上次 API 响应之后新增的 items"，用字节 heuristic 估算它们的 tokens，加到 API 返回的 total 上。

```rust
// ref/codex: context_manager/history.rs
pub(crate) fn get_total_token_usage(&self, server_reasoning_included: bool) -> i64 {
    let last_tokens = self.token_info
        .as_ref()
        .map(|info| info.last_token_usage.total_tokens)
        .unwrap_or(0);
    let items_after = self.items_after_last_model_generated_item()
        .iter()
        .map(estimate_item_token_count)
        .fold(0i64, i64::saturating_add);
    if server_reasoning_included {
        last_tokens.saturating_add(items_after)
    } else {
        last_tokens
            .saturating_add(self.get_non_last_reasoning_items_tokens())
            .saturating_add(items_after)
    }
}
```

这种双层策略的好处是：**不需要本地 tokenizer**。本地估算只用于增量部分，精确的 token 计数来自 API 响应。当两者相差太大时，说明估算有偏差，但下一次 API 调用会纠正。

### 3.3 DeepOmni 的 ContextManager：精简版

DeepOmni 的 `ContextManager` 是 Codex 版本的精简实现：

```rust
// crates/deepomni-context/src/lib.rs
pub struct ContextManager {
    items: Vec<ModelMessage>,
    history_version: u64,
    token_info: Option<TokenUsageInfo>,
    reference_context: Option<ContextSnapshot>,
}
```

对比：

| 能力 | Codex | DeepOmni |
|------|-------|----------|
| 历史记录 | `record_items()` + TruncationPolicy | `record_items()` + TruncationPolicy ✅ |
| 构造 prompt | `for_prompt()` with normalization | `for_prompt()` 直接 clone ⚠️ |
| 版本追踪 | `history_version` | `history_version` ✅ |
| Token 追踪 | 双层（API usage + 本地估算） | 单层（API usage only）⚠️ |
| Normalization | 三步曲（call/output 配对、孤立清理、图片剥离） | 无 ❌ |
| Rollback | `drop_last_n_user_turns()` | 无 ❌ |
| 删除最旧项 | `remove_first_item()` with 配对清理 | 仅 truncation 策略 |
| 图片处理 | `replace_last_turn_images()` | 无 ❌ |
| Reference context | `TurnContextItem`（用于 diffing） | `ContextSnapshot`（用于快照） ✅ |

**关键差距一：无 normalization**。DeepOmni 的 `for_prompt()` 直接 clone items 返回，没有检查 call/output 配对完整性。如果 compaction 删除了一个 tool call 但保留了它的 output，模型 API 可能会报错。

**关键差距二：无 rollback**。Codex 支持 `drop_last_n_user_turns()`，可以按 turn 边界回退历史。这在用户说"撤销上一步"或 compaction 出错时非常有用。DeepOmni 没有这个能力。

**关键差距三：token 追踪只有一层**。DeepOmni 只记录 API 返回的 usage，没有估算本地新增项的 tokens。这意味着在两次 API 调用之间，`needs_compaction()` 的判断可能不准确——特别是当用户输入了大量文本或工具输出了大量内容时。

## 4. Token Budget：固定比例分配 vs 动态调整

### 4.1 DeepOmni 的 TokenBudget：V1 固定比例

DeepOmni 实现了一个简洁的 `TokenBudget` 系统，按固定比例分配 token 预算：

```rust
// crates/deepomni-context/src/lib.rs
pub struct TokenBudget {
    pub total: u64,
    pub system_tokens: u64,      // 10%
    pub schema_tokens: u64,      // 10%
    pub skill_tokens: u64,       // 10%
    pub history_tokens: u64,     // 65%
    pub margin_tokens: u64,      // 5%
    pub consumed: u64,
}
```

这个设计的优点是**确定性**——给定 total，每个 bucket 的大小是固定的。调试和推理都很容易。缺点是**不灵活**——如果某个 turn 没有 skills（10% 浪费了），或者 tool schemas 很少（10% 又浪费了），history 拿不到这些余量。

### 4.2 Codex 的 TruncationPolicy：按 item 级别控制

Codex 没有一个统一的 `TokenBudget` struct。它的 token 控制分散在两层：

**第一层：TruncationPolicy**。在 `record_items()` 时传入，控制单个 tool output 的截断：

```rust
// ref/codex: codex-rs/core/src/context_manager/history.rs
fn process_item(&self, item: &ResponseItem, policy: TruncationPolicy) -> ResponseItem {
    let policy_with_serialization_budget = policy * 1.2; // 留 20% 序列化余量
    match item {
        ResponseItem::FunctionCallOutput { call_id, output } => {
            ResponseItem::FunctionCallOutput {
                call_id: call_id.clone(),
                output: truncate_function_output_payload(output, policy_with_serialization_budget),
            }
        }
        // CustomToolCallOutput 类似处理
        _ => item.clone(), // 非 tool output 不截断
    }
}
```

这意味着 Codex 的截断是**在 item 级别**发生的——一个 5000 token 的 `cat` 输出可以被截断到 2000 token，而不是整个 item 被丢弃。而 DeepOmni 的 `TruncationPolicy::TokenBudget` 是**在 history 级别**的——它会丢弃最旧的整个 item，而不是截断单个 item 的内容。

**第二层：context window 级别的 compaction 触发**。当 `get_total_token_usage()` 接近 `model_context_window` 时，Codex 触发 compaction task，把整个历史压缩成摘要。

### 4.3 DeepOmni 的 assemble_context：确定性溢出策略

DeepOmni 的 `assemble_context()` 函数实现了 PRD §24.3 定义的五级确定性溢出策略：

```
溢出优先级（从最先丢弃到最后丢弃）：
1. 低优先级 plugin capability 摘要
2. 非活跃 skill 描述
3. 大型 tool output（截断到一半）
4. 最旧的对话消息
5. 受保护项（system, tool result, reasoning replay）——永不丢弃
```

这比 Codex 的方案**更系统化**——Codex 的溢出处理分散在 `TruncationPolicy`、`compact.rs`、`regular.rs` 等多个地方，没有一个统一的优先级梯度。DeepOmni 把它集中在一个函数里，逻辑清晰，行为确定。

但 DeepOmni 的 `assemble_context()` 缺少一个关键能力：**它不做 normalization**。即使它正确地丢弃了某些 items，剩余的 items 可能存在 call/output 配对不完整的问题。

## 5. Compaction：模型驱动的历史压缩

### 5.1 Codex 的三种 Compaction 策略

Codex 的 compaction 是一个复杂且精心设计的系统。它支持三种策略，根据模型 provider 的能力自动选择：

**策略一：Local Compact（本地摘要）**

当 provider 不支持 remote compaction 时使用。流程：

```
1. 克隆当前历史
2. 把 SUMMARIZATION_PROMPT（prompt.md 模板）作为用户输入追加到历史
3. 发送给模型，让模型生成摘要
4. 用 "摘要前缀 + 模型输出的摘要" 替换整个历史
5. 保留最近的用户消息（不压缩）
6. 清除 reference_context_item，让下一轮完整重新注入初始上下文
```

核心代码（简化）：

```rust
// ref/codex: codex-rs/core/src/compact.rs
async fn run_compact_task_inner_impl(
    sess: Arc<Session>,
    turn_context: Arc<TurnContext>,
    input: Vec<UserInput>,
    initial_context_injection: InitialContextInjection,
) -> CodexResult<String> {
    // 1. 构造 compaction prompt
    let mut history = sess.clone_history().await;
    history.record_items(&[initial_input_for_turn.into()], turn_context.truncation_policy);

    // 2. 发送给模型
    loop {
        let prompt = Prompt {
            input: history.clone().for_prompt(&turn_context.model_info.input_modalities),
            base_instructions: sess.get_base_instructions().await,
            ..Default::default()
        };
        match drain_to_completed(&sess, &turn_context, &mut client_session, &prompt).await {
            Ok(()) => break,
            Err(CodexErr::ContextWindowExceeded) => {
                // 即使在 compaction 时也可能 context window exceeded
                // → 删除最旧的 item，重试
                history.remove_first_item();
                continue;
            }
            Err(e) => { /* 重试 or 失败 */ }
        }
    }

    // 3. 构造压缩后的历史
    let summary_suffix = get_last_assistant_message_from_turn(history.raw_items());
    let summary_text = format!("{SUMMARY_PREFIX}\n{summary_suffix}");
    let user_messages = collect_user_messages(history.raw_items());
    let new_history = build_compacted_history(Vec::new(), &user_messages, &summary_text);

    // 4. 替换历史
    sess.replace_compacted_history(new_history, reference_context_item, compacted_item).await;

    // 5. 重算 token usage
    sess.recompute_token_usage(&turn_context).await;

    // 6. 发出警告
    sess.send_event(&turn_context, EventMsg::Warning(WarningEvent {
        message: "Heads up: Long threads and multiple compactions can cause the model to be less accurate. Start a new thread when possible...".to_string(),
    })).await;

    Ok(summary_suffix)
}
```

注意第 6 步的警告：Codex 在 compaction 后会主动提醒用户"长线程和多次压缩可能降低模型准确性，建议开新线程"。这不是客套话——compaction 本质上是信息有损的，模型看到的是摘要而不是原始对话。

**策略二：Remote Compact（远端压缩）**

当 provider 支持 `supports_remote_compaction()` 时使用。这是 OpenAI Responses API 的特性——服务端可以自动管理上下文窗口，客户端不需要手动摘要。Codex 的 `compact_remote.rs` 和 `compact_remote_v2.rs` 实现了两个版本的远端压缩协议。

**策略三：Inline Auto-Compact（mid-turn 自动压缩）**

这是最有意思的一种。当一个 turn 执行到中途时，如果 token usage 超过阈值，Codex 可以**在 turn 内部**触发 compaction，而不是等到 turn 结束。这通过 `InitialContextInjection::BeforeLastUserMessage` 参数控制——压缩后的历史需要在最后一条用户消息之前重新注入初始上下文，因为模型被训练为在 compaction 后看到摘要作为历史的最后一项。

### 5.2 Compaction 的触发机制

Codex 的 compaction 有两个触发时机：

**自动触发（Auto Compact）**

在 `regular.rs` 的 `run_turn` 循环中，每次模型 API 返回后检查 token usage：

```
if total_tokens / context_window >= threshold:
    run_inline_auto_compact_task()
```

阈值是可配置的，默认约 80%。

**手动触发（Manual Compact）**

用户通过 `Op::ManualCompact`（或等价操作）显式请求压缩。这会创建一个 `CompactTask`，走 `SessionTask` 的 spawn 流程。

### 5.3 Compaction 的 Hook 系统

Codex 的 compaction 不是"直接压缩完事"。它有 pre-compact 和 post-compact hook：

```rust
// ref/codex: compact.rs (run_compact_task_inner 实际源码)
let pre_compact_outcome = run_pre_compact_hooks(&sess, &turn_context, trigger).await;
match pre_compact_outcome {
    PreCompactHookOutcome::Continue => {}
    PreCompactHookOutcome::Stopped { reason } => {
        let error = reason.unwrap_or_else(|| "PreCompact hook stopped execution".to_string());
        attempt.track(sess.as_ref(), CompactionStatus::Interrupted, Some(error)).await;
        return Err(CodexErr::TurnAborted);
    }
}

// 执行 compaction 核心逻辑（run_compact_task_inner_impl）
let result = run_compact_task_inner_impl(
    Arc::clone(&sess),
    Arc::clone(&turn_context),
    input,
    initial_context_injection,
).await;

// 追踪 compaction 状态
let status = compaction_status_from_result(&result);
let error = result.as_ref().err().map(ToString::to_string);

if result.is_ok() {
    let post_compact_outcome = run_post_compact_hooks(&sess, &turn_context, trigger).await;
    if let PostCompactHookOutcome::Stopped = post_compact_outcome {
        attempt.track(sess.as_ref(), status, error).await;
        return Err(CodexErr::TurnAborted);
    }
}
attempt.track(sess.as_ref(), status, error).await;
result.map(|_| ())
```

这允许用户通过 hook 脚本在 compaction 前后执行自定义逻辑：比如在 pre-compact hook 里把当前历史保存到外部存储，或在 post-compact hook 里验证摘要质量。

### 5.5 Claude Code 的 AutoCompactTracker

Claude Code 的 compaction 更简单。它在 `query()` 的状态里维护了一个 `AutoCompactTracker`：

```typescript
// ref/claude-code: src/services/compact/autoCompact.ts (实际源码)
export type AutoCompactTrackingState = {
    compacted: boolean
    turnCounter: number
    turnId: string               // 每轮唯一 ID
    consecutiveFailures?: number // 连续失败次数，用作熔断器
}

// 阈值计算：effective context window - 13K buffer
export function getAutoCompactThreshold(model: string): number {
    const effectiveContextWindow = getEffectiveContextWindowSize(model)
    return effectiveContextWindow - AUTOCOMPACT_BUFFER_TOKENS // 13_000
}

// 判断是否需要 autocompact
export async function shouldAutoCompact(
    messages: Message[],
    model: string,
    querySource?: QuerySource,
    snipTokensFreed = 0,
): Promise<boolean> {
    if (querySource === 'session_memory' || querySource === 'compact') return false
    if (!isAutoCompactEnabled()) return false
    const threshold = getAutoCompactThreshold(model)
    const tokenCount = tokenCountWithEstimation(messages, model)
    return (tokenCount - snipTokensFreed) >= threshold
}

// 连续失败 3 次后停止重试（熔断器）
const MAX_CONSECUTIVE_AUTOCOMPACT_FAILURES = 3
```

```typescript
// ref/claude-code: src/query.ts (query loop 中调用 autocompact 的实际代码)
const { compactionResult, consecutiveFailures } = await deps.autocompact(
    messagesForQuery,
    toolUseContext,
    { systemPrompt, userContext, systemContext, toolUseContext, forkContextMessages: messagesForQuery },
    querySource,
    tracking,
    snipTokensFreed,
)

if (compactionResult) {
    // 重置 tracking 状态
    tracking = { compacted: true, turnId: deps.uuid(), turnCounter: 0, consecutiveFailures: 0 }
    // 用压缩后的 messages 替换当前 messages
    const postCompactMessages = buildPostCompactMessages(compactionResult)
    for (const message of postCompactMessages) { yield message }
}
```

关键差异：
- Claude Code 的 compaction 在 query loop 内作为 `deps.autocompact()` 同步调用，不是独立的 task。但它**有 pre/post compact hooks**（`executePreCompactHooks` / `executePostCompactHooks`）。
- Claude Code **有 analytics**——通过 `logEvent('tengu_auto_compact_succeeded', ...)` 追踪 compaction 的触发频率、token 变化、compaction 本身的 token 消耗。
- Claude Code 还有**熔断器机制**——连续失败 3 次后停止重试，避免浪费 API 调用。
- Claude Code 除了 autocompact，还有 **microcompact**（细粒度压缩）、**snip**（片段裁剪）、**context collapse**（上下文折叠）等多层压缩策略。

### 5.6 DeepOmni 的 Compaction：阈值检测与历史替换

DeepOmni 在 `ContextManager` 中提供了 compaction 的基础设施：

```rust
// crates/deepomni-context/src/lib.rs
impl ContextManager {
    /// 检测是否需要 compaction：prompt_tokens / context_window >= threshold
    pub fn needs_compaction(&self, threshold: f64) -> bool {
        let Some(info) = &self.token_info else { return false };
        let Some(window) = info.context_window else { return false };
        if window == 0 { return false }
        (info.total_tokens as f64 / window as f64) >= threshold
    }

    /// 用压缩后的 items 替换整个历史，并递增 history_version
    pub fn replace_history(&mut self, items: Vec<ModelMessage>) {
        self.items = items;
        self.history_version = self.history_version.saturating_add(1);
    }

    /// 快照当前历史状态（items + version + token_info）
    pub fn snapshot(&self) -> ContextSnapshot {
        ContextSnapshot {
            items: self.items.clone(),
            history_version: self.history_version,
            token_info: self.token_info.clone(),
        }
    }

    /// 保存当前状态为参考上下文（compaction 前的基线）
    pub fn set_reference_context(&mut self) {
        self.reference_context = Some(self.snapshot());
    }
}
```

当前 DeepOmni 的 compaction 能力处于**第一层防线**阶段：`assemble_context()` 的确定性溢出策略可以通过丢弃低优先级 fragment 和截断大型 tool output 来控制上下文大小。`needs_compaction()` + `replace_history()` 提供了模型驱动摘要压缩所需的检测和替换接口，但**摘要生成流程**（调用模型生成摘要、构造压缩后历史、发出 compaction event）、**hook 系统**和 **analytics 追踪**需要在 agent loop 中集成。

## 6. Prompt 构建：五层优先级系统

### 6.1 DeepOmni 的 PromptBuilder

DeepOmni 实现了一个清晰的五层 prompt 构建系统：

```rust
// crates/deepomni-context/src/lib.rs
pub struct PromptBuilder {
    pub override_prompt: Option<String>,  // Layer 1: 最高优先级覆盖
    pub agent_prompt: Option<String>,     // Layer 2: Agent/子agent 特定提示
    pub custom_prompt: Option<String>,    // Layer 3: 用户自定义提示
    pub default_prompt: String,           // Layer 4: DeepOmni 默认提示
    pub append_prompt: Option<String>,    // Layer 5: 始终追加的后记
}
```

优先级规则：
1. **Override** 存在时，替换所有其他层，直接返回。
2. **Agent** 存在时，替换 Custom 和 Default，但 Append 仍然追加。
3. **Custom** 存在时，替换 Default。
4. **Default** 是兜底。
5. **Append** 始终追加（安全规则、工具约束等）。

`BuiltPrompt` 还包含 `static_hash`（SHA-256），用于检测 prompt 是否命中缓存——如果两次 turn 的 static prompt 相同，provider 可以复用 KV cache。

### 6.2 Codex 的 Prompt 构造

Codex 的 prompt 构造分散在 `Prompt` struct 和 `build_initial_context()` 中：

```rust
// ref/codex: codex-rs/core/src/client_common.rs (实际源码)
pub struct Prompt {
    /// 会话上下文输入项（历史 items）
    pub input: Vec<ResponseItem>,
    /// 模型可用工具列表（含 MCP 外部工具）
    pub(crate) tools: Vec<ToolSpec>,
    /// 是否允许并行工具调用
    pub(crate) parallel_tool_calls: bool,
    /// 模型基础指令
    pub base_instructions: BaseInstructions,
    /// personality 偏好
    pub personality: Option<Personality>,
    /// 可选的输出 schema（用于约束模型最终输出的 JSON 格式）
    pub output_schema: Option<Value>,
    /// 是否严格验证 output_schema
    pub output_schema_strict: bool,
}
```

Codex 不用"五层优先级"这种模式。它的 prompt 是由多个组件拼装的：
1. `base_instructions` 来自 `model_info.get_model_instructions(personality)`
2. 初始上下文（environment, user instructions, skills, plugins）作为 developer messages 注入到 history 的开头
3. Tools 和 reasoning 配置作为 API 参数传递

差异的根源在于：Codex 面向的是 OpenAI Responses API，prompt 结构由 API schema 定义；DeepOmni 需要支持多 provider，prompt 构建需要更高的抽象层次。

## 8. 上下文工程的三个核心原则

### 8.1 Codex 的原则

**原则一：历史是有版本的。每次修改都递增 history_version。**

这不是学术上的"版本控制"，而是工程上的必要性。当两个并发任务都想修改历史时（比如一个 tool 正在往历史里追加输出，同时 auto-compact 想替换历史），version 可以检测冲突。Codex 的 `history_version` 配合 `reference_context_item` 实现了一种简单的乐观并发控制。

**原则二：Normalization 是不可跳过的。每次 for_prompt() 都要 normalize。**

不管历史是怎么被修改的（record、replace、rollback、compaction），在送入模型之前都必须检查结构完整性。孤立的 tool output 或缺失的 function call 会导致 API 错误。

**原则三：Compaction 是有损的。用户必须被告知。**

Codex 在 compaction 后主动发出 warning event。它不试图隐藏 compaction 的副作用。长线程 + 多次 compaction = 模型质量下降，这是当前大模型架构的固有限制。

### 8.2 Claude Code 的原则

**原则一：上下文每轮重新构造，不做增量 diff。**

Claude Code 的 developer messages 不进入持久化历史。每轮都重新生成环境信息、工具描述、自定义指令。这简化了状态管理，但代价是每轮都要花 tokens 重新发送这些不变的内容。

**原则二：Compaction 是 query loop 内的同步操作。**

不需要独立的 task、hook、analytics。简单直接。适合 Claude Code 的"集成式 runtime"架构。

### 8.3 对 DeepOmni 的启示

DeepOmni 应该走 Codex 的路线（因为它的目标是可复用的 agent harness），但可以从 Claude Code 借鉴一些简洁性：

1. **补齐 normalization**：在 `for_prompt()` 里加入 call/output 配对检查和孤立清理。这是最紧急的——没有 normalization，compaction 后的历史可能导致 API 错误。

2. **实现模型驱动的 compaction**：当前的 `assemble_context()` 确定性溢出策略是好的第一层防线，但它只能"丢弃"不能"摘要"。需要加入 Codex 式的"调用模型生成摘要"流程。

3. **补充 token 追踪的第二层**：在本地估算新增 items 的 tokens，让 `needs_compaction()` 的判断更准确。

4. **实现 rollback**：`drop_last_n_user_turns()` 是一个高价值的能力。当用户说"撤销"或 agent 陷入错误循环时，rollback 比 compaction 更精确。

5. **丰富 TurnExecutionContext**：从 6 字段扩展到至少包含 cwd、permission_profile、truncation_policy、features。这些字段直接影响工具执行和上下文构建的行为。
