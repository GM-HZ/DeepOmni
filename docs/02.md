## 1. 引言：工具不是一个函数数组

博客第 2 篇开门见山地指出了一个常见误解：

> 如果只看概念，agent loop 很简单：`model -> action -> observation -> model`。但工程上真正难的不是"让模型说我要运行测试"，而是：模型看到的工具 schema 和真实执行实现如何分离？一个工具会不会修改文件、启动进程、访问网络，谁说了算？并行工具调用如何避免互相踩状态？`apply_patch` 为什么不能只是 shell 里的一段命令？MCP / Apps / Hooks 这种外部扩展如何接进来，又不把 core 搞成一堆特判？

这段话揭示了 coding agent 工具系统的核心复杂度：**工具能力越强，越需要把"能力"和"约束能力的边界"一起设计**。

Codex 的回答是一条 **五层管线**：

```
ToolSpec（模型看到的 schema）
  → ToolRouter（把模型输出还原成内部 ToolCall）
    → ToolCallRuntime（并行 / 串行控制）
      → ToolRegistry（统一分发 + hooks + telemetry + mutating gate）
        → ToolOrchestrator / Sandbox（审批 + 沙箱 attempt）
          → Handler Runtime（实际执行）
```

Claude Code 的工具系统则更像一个**集成式应用层**：`Tool` 类型直接接触 UI、permission、MCP、agent 等应用状态，一个 `call` 方法可以做完所有事情。

这两种方式各有其合理性。本文将逐层剖析 Codex 的管线设计，并对照 Claude Code 和 DeepOmni 的当前实现，提炼出可落地的架构指导。

## 2. 第一层：ToolSpec——模型可见 Schema

### 2.1 Codex：模型看到的是 spec，core 持有的是 handler

工具在 `build_prompt` 时注入模型请求。`Prompt.tools` 来自 `router.model_visible_specs()`，不是来自某个 handler 直接暴露。

工具集合的构造在 `build_specs_with_discoverable_tools`，会把几类工具来源统一规划：

```
内置工具：apply_patch、view_image、unified_exec
MCP / Apps 工具
deferred MCP tools（延迟加载的 MCP 工具）
dynamic / discoverable tools（动态发现的工具）
多 Agent 工具
tool_search / tool_suggest（懒加载入口）
```

规划结果分成两类：

1. **model-visible `ToolSpec`**：模型需要知道"我可以调用什么，参数 schema 是什么"。
2. **core-side `ToolHandler`**：core 需要知道"这个工具由谁处理、是否支持并行、是否可能修改环境、执行前后有哪些 hook、失败如何反馈给模型"。

这层分离非常重要。它让 Codex 可以支持 **lazy tool discovery**：工具世界可以很大（几百个 MCP tools），但模型每次看到的工具集合应该尽量小、尽量确定。`tool_search` / `tool_suggest` 的存在，就是为了在工具空间很大时，仍然让模型只在需要时展开能力。

### 2.2 Claude Code：Tool 类型直接关联上下文

Claude Code 的 `Tool` 类型定义直接把 spec 和 handler 放在一起：

```typescript
// ref/claude-code: src/Tool.ts
export type Tool = {
    name: string;
    description: string;
    inputSchema: JSONSchema;
    isReadOnly: boolean;
    // call 方法可以访问完整的应用上下文
    call: (input: ToolInput, context: ToolUseContext) => Promise<ToolOutput>;
    // 权限相关
    isEnabled?: (context: ToolUseContext) => boolean;
    needsPermission?: (input: ToolInput, context: ToolUseContext) => PermissionResult;
};
```

`ToolUseContext` 里带了 `abortController`、`cwd`、`tools`、`permissions`、`setToolJSX`、`appendSystemMessage`、`sendOSNotification` 等运行时状态。一个 Tool 的上下文不仅知道"如何执行"，还知道应用运行时的很多东西。

这种设计的好处是功能接入路径短；代价是工具和应用运行时强耦合——你无法在不同的 runtime 环境（如 headless worker、remote sandbox）里复用同一个 Tool 定义。

### 2.3 DeepOmni 当前：ToolSpec 与 ToolHandler 已分离，但缺少 Router

DeepOmni 的 `ToolHandler` trait 已经把 spec 和 handler 分开：

```rust
// crates/deepomni-tools/src/lib.rs
pub trait ToolHandler: Send + Sync {
    fn name(&self) -> &str;
    fn spec(&self) -> Option<ToolSpec> { None }
    fn is_mutating(&self) -> bool { false }
    fn supports_parallel(&self) -> bool { false }
    fn approval_default(&self) -> ApprovalDefault { ApprovalDefault::Auto }
    fn capabilities(&self) -> Vec<ToolCapability> { vec![ToolCapability::ReadOnly] }
    fn sandbox_preference(&self) -> SandboxPreference { SandboxPreference::Unsandboxed }
    async fn handle(&self, invocation: ToolInvocation) -> Result<ToolOutput, ToolError>;
}
```

`ToolSpec` 通过 `handler.spec()` 获取，用于注入模型请求；`ToolHandler` 的其他方法（`is_mutating`、`supports_parallel`、`approval_default` 等）提供 policy 元数据，用于 core 决策。

**但缺少 Router 层**：ToolRegistry 既管 spec cache 又管 dispatch，没有"把模型输出还原成内部 ToolCall"的中间层。这意味着模型 API 如果有多种工具表达方式（FunctionCall / CustomToolCall / LocalShellCall / ToolSearchCall），后面的执行层需要到处判断。

## 3. 第二层：ToolRouter——把模型输出还原成内部 ToolCall

### 3.1 为什么需要 Router

博客第 2 篇解释了这一层的必要性：

> 模型流里出现 `OutputItemDone` 时，Codex 调 `handle_output_item_done`。这里先调用 `ToolRouter::build_tool_call`，把不同形态的 `ResponseItem` 还原为内部 `ToolCall`。

Codex 需要处理的模型输出形态至少有四种：

```rust
// ref/codex: 从 ResponseItem 到内部 ToolCall 的转换
match response_item {
    ResponseItem::FunctionCall { name, arguments, call_id, .. } => {
        // 普通 function tool
        // 如果命中 MCP tool info，转成 ToolPayload::Mcp
        ToolCall { tool_name: name, call_id, payload: ToolPayload::Function { arguments } }
    }
    ResponseItem::ToolSearchCall { query, .. } => {
        // 客户端执行的 tool_search
        ToolCall { tool_name: "tool_search", payload: ToolPayload::Search { query } }
    }
    ResponseItem::CustomToolCall { name, arguments, .. } => {
        // Responses API custom tool
        ToolCall { tool_name: name, payload: ToolPayload::Custom { arguments } }
    }
    ResponseItem::LocalShellCall { command, .. } => {
        // 转成 local_shell 对应逻辑
        ToolCall { tool_name: "local_shell", payload: ToolPayload::Shell { command } }
    }
}
```

`ToolRouter` 的职责：

```rust
// ref/codex: core/src/tools/router.rs
pub struct ToolRouter {
    registry: Arc<ToolRegistry>,
    /// 所有已注册工具的 spec（包括不可见的）
    all_specs: Vec<ToolSpec>,
    /// 当前模型可见的 spec 子集
    model_visible_specs: Vec<ToolSpec>,
    /// 允许并行执行的 MCP server 名集合
    parallel_mcp_server_names: HashSet<String>,
}

impl ToolRouter {
    /// 从 config 构建 router，过滤 deferred dynamic tools
    pub fn from_config(config: &ToolsConfig, registry: Arc<ToolRegistry>) -> Self;

    /// 返回当前模型可见的工具集合
    pub fn model_visible_specs(&self) -> &[ToolSpec];

    /// 把模型输出还原成内部 ToolCall
    pub fn build_tool_call(&self, item: &ResponseItem) -> Option<ToolCall>;

    /// 判断一个工具是否支持并行执行
    pub fn supports_parallel(&self, tool_name: &str) -> bool;
}
```

Router 的关键价值在于：**后面的执行层只需要统一处理 `ToolCall { tool_name, call_id, payload }` 就够了**。不需要在 Runtime、Registry、Handler 里到处判断 `ResponseItem` 的具体形态。

### 3.2 MCP 工具的名字清洗与还原

Router 还承担了一个隐蔽但重要的职责：**MCP 工具名字的清洗和还原**。

MCP 工具的 model-visible name 可能经过清洗、去重、hash，以适配 API 命名限制（比如 OpenAI function call 对名字有长度和字符限制）。但执行时必须知道原始的 `server + raw tool name + raw arguments`。

```
模型看到的名字：  mcp_github_repo_list_files_a7f3b2
                    ↑ prefix  ↑ cleaned name      ↑ hash
Router 还原后：    server = "github"
                  tool = "repo_list_files"
                  arguments = { raw JSON }
```

Codex 在 router 阶段完成这个还原，后面 MCP handler 才能准确调用对应 server。

### 3.3 对 DeepOmni 的启示

DeepOmni 当前没有 Router 层。`ToolRegistry.dispatch(invocation)` 直接拿 `tool_name` 查 handler。这在只有内置工具时没问题，但一旦引入 MCP tools、dynamic tools、tool_search，就需要一个中间翻译层。

建议增加 `ToolRouter`：

```rust
// 目标：crates/deepomni-tools/src/router.rs
pub struct ToolRouter {
    registry: Arc<ToolRegistry>,
    model_visible_specs: Vec<ToolSpec>,
    mcp_tool_mappings: HashMap<String, McpToolInfo>, // cleaned name → server+raw name
}

impl ToolRouter {
    pub fn model_visible_specs(&self) -> &[ToolSpec];
    pub fn build_tool_call(&self, tool_name: &str, arguments: serde_json::Value) -> ToolCall;
    pub fn supports_parallel(&self, tool_name: &str) -> bool;
}
```

## 4. 第三层：ToolCallRuntime——并行 / 串行控制

### 4.1 Codex 的 RwLock 方案

这是博客第 2 篇中最巧妙的设计之一。`ToolCallRuntime` 用一个 `RwLock<()>` 来控制工具并行度：

```rust
// ref/codex: core/src/agent/tool_call_runtime.rs
pub struct ToolCallRuntime {
    router: Arc<ToolRouter>,
    session: Arc<Session>,
    turn_context: Arc<TurnContext>,
    tracker: Arc<ToolCallTracker>,
    /// 读锁 = 可并行（非 mutating），写锁 = 独占（mutating）
    parallel_execution: Arc<RwLock<()>>,
}

impl ToolCallRuntime {
    async fn handle_tool_call_with_source(&self, tool_call: ToolCall) -> ToolCallResult {
        let supports_parallel = self.router.supports_parallel(&tool_call.tool_name);

        if supports_parallel {
            // 拿读锁，可以和其他读锁持有者并行
            let _guard = self.parallel_execution.read().await;
            self.execute(tool_call).await
        } else {
            // 拿写锁，独占执行
            let _guard = self.parallel_execution.write().await;
            self.execute(tool_call).await
        }
    }
}
```

博客原文评价这个设计：

> 这个设计很朴素，但非常实用：`list_dir`、某些只读 MCP 工具可以并行。shell、patch、会改文件的工具通常应该串行。如果模型一次返回多个工具调用，runtime 不需要为每个工具写一套并发策略。这里不是为了追求极致吞吐，而是为了维持一个可解释的状态边界：**读可以并发，写要保守串行**。

### 4.2 Claude Code 的 StreamingToolExecutor

Claude Code 的并行控制更复杂，因为它支持**边流式边执行**：

```typescript
// ref/claude-code: src/services/tools/StreamingToolExecutor.ts
type ToolStatus = 'queued' | 'executing' | 'completed' | 'yielded';

type TrackedTool = {
    id: string;
    block: ToolUseBlock;
    status: ToolStatus;
    isConcurrencySafe: boolean;
    promise?: Promise<void>;
    results?: Message[];
    pendingProgress: Message[];
};

export class StreamingToolExecutor {
    private tools: TrackedTool[] = [];
    private siblingAbortController: AbortController;

    addTool(block: ToolUseBlock, assistantMessage: AssistantMessage): void {
        const isConcurrencySafe = toolDefinition?.isReadOnly ?? false;
        this.tools.push({
            id: block.id,
            block,
            status: 'queued',
            isConcurrencySafe,
            pendingProgress: [],
        });
        this.maybeStartTools();
    }

    private maybeStartTools(): void {
        const hasExclusiveRunning = this.tools.some(
            t => t.status === 'executing' && !t.isConcurrencySafe
        );
        const hasAnyRunning = this.tools.some(t => t.status === 'executing');

        for (const tool of this.tools) {
            if (tool.status !== 'queued') continue;

            if (tool.isConcurrencySafe && !hasExclusiveRunning) {
                this.startTool(tool);
            } else if (!tool.isConcurrencySafe && !hasAnyRunning) {
                this.startTool(tool);
            }
        }
    }
}
```

关键差异对比：

| 维度 | Codex `ToolCallRuntime` | Claude Code `StreamingToolExecutor` |
|------|------------------------|-------------------------------------|
| 启动时机 | 一个 turn step 完成后批量执行 | 模型还在流式输出时就开始执行 |
| 并行控制 | `RwLock<()>` 读写锁 | `isConcurrencySafe` + 状态机 |
| 取消机制 | turn-level cancellation | `siblingAbortController`（一个 bash 出错，取消所有兄弟） |
| 结果顺序 | 按执行完成顺序 | 按工具到达顺序（buffer + yield） |
| 进度报告 | 通过 EventMsg 回流 | `pendingProgress` 数组 + yield |

### 4.3 DeepOmni 当前：严格串行

DeepOmni 的 `run_turn` 里，工具是在流式循环内逐个执行的：

```rust
// crates/deepomni-agent/src/lib.rs (当前)
Some(ModelDelta::ToolCallComplete { .. }) => {
    // 1. 评估审批
    let decision = ToolOrchestrator::evaluate_with_cache(...);
    match decision {
        OrchestratorDecision::Proceed { .. } => {
            // 2. 直接执行（串行）
            let result = self.execute_tool(&tc, &arguments, &ctx).await?;
            // 3. 构造 tool result message
            iteration_tool_results.push(ModelMessage { role: Tool, content: result.content, .. });
        }
        OrchestratorDecision::NeedsApproval { .. } => {
            return Ok(TurnResult::NeedsApproval { .. });
        }
        OrchestratorDecision::Forbidden { .. } => { /* emit error */ }
    }
}
```

问题在于：如果模型一次返回 3 个 `list_dir` 调用，它们会串行执行。而这 3 个都是只读工具，完全可以并行。

好消息是 DeepOmni 的 `ToolHandler` trait **已经定义了 `supports_parallel()` 和 `is_mutating()`** 方法，只是没有被使用。引入 `ToolCallRuntime` 只需要：

1. 在 `run_turn` 的流式循环内，把 tool calls 收集到一个 `Vec<PendingToolCall>` 里，而不是逐个执行
2. 流式循环一个 step 结束后，通过 `ToolCallRuntime::execute_batch` 批量执行
3. `execute_batch` 内部用 `RwLock` 控制并行度

## 5. 第四层：ToolRegistry——统一分发、Hooks 和 Mutating Gate

### 5.1 Codex 的 dispatch_any

`ToolRegistry::dispatch_any` 是工具分发中心。博客把它的职责压缩成了伪代码：

```
handler = registry.lookup(tool_name)
ensure payload kind matches handler kind
pre_result = run_pre_tool_use_hooks(handler, payload)
if pre_result blocks:
    return blocked output
if handler.is_mutating():
    wait for tool_call_gate
output = handler.handle(payload, runtime_context)
post_result = run_post_tool_use_hooks(handler, output)
record telemetry / trace
return output as ResponseInputItem
```

这段伪代码的重点：

1. **Hooks 不是模型工具**。hooks 是工具执行链旁边的策略扩展点。pre hook 可以阻止执行；post hook 可以追加上下文、停止流程、替换反馈给模型的结果。
2. **`is_mutating()` 和 `tool_call_gate`**。Codex 没有假设所有工具都同样安全。mutating 工具需要等待 gate（可能是审批、可能是 sandbox 准备）。
3. **Telemetry 和 trace 在 registry 层统一记录**，不需要每个 handler 自己写。

博客原文强调了 hooks 的定位：

> hooks 不是模型工具。hooks 是工具执行链旁边的策略扩展点。pre hook 可以阻止执行；post hook 可以追加上下文、停止流程、替换反馈给模型的结果。这样 hooks 能影响 agent 行为，但不需要被暴露成模型可调用工具。模型工具调用是 untrusted input；hook command 是用户配置的 trusted policy surface。两者必须分开看。

### 5.2 ToolHandler trait 的扩展点

Codex 的 `ToolHandler` trait 比 DeepOmni 的更丰富：

```rust
// ref/codex: 对比两者的 ToolHandler trait

// Codex ToolHandler：
trait ToolHandler {
    fn kind(&self) -> ToolKind;           // 工具类型（function/mcp/custom/...）
    fn matches_kind(&self, payload: &ToolPayload) -> bool;  // payload 类型匹配
    fn is_mutating(&self) -> bool;        // 是否可能修改环境
    fn pre_tool_use_payload(&self) -> PreToolUsePayload;    // pre-hook payload
    fn post_tool_use_payload(&self, output: &ToolOutput) -> PostToolUsePayload;  // post-hook payload
    fn create_diff_consumer(&self) -> Option<DiffConsumer>;  // diff 追踪
    async fn handle(&self, payload: ToolPayload, ctx: &ToolRuntimeContext) -> ToolOutput;
}

// DeepOmni ToolHandler（当前）：
trait ToolHandler {
    fn name(&self) -> &str;
    fn spec(&self) -> Option<ToolSpec>;
    fn is_mutating(&self) -> bool;
    fn supports_parallel(&self) -> bool;
    fn approval_default(&self) -> ApprovalDefault;
    fn capabilities(&self) -> Vec<ToolCapability>;
    fn sandbox_preference(&self) -> SandboxPreference;
    async fn handle(&self, invocation: ToolInvocation) -> Result<ToolOutput, ToolError>;
}
```

DeepOmni 已经有了 `is_mutating`、`supports_parallel`、`approval_default`、`sandbox_preference` 这些策略声明方法——这比很多 agent 项目都要完善。缺少的是：

1. **`kind` / `matches_kind`**：当支持多种工具来源（native / MCP / plugin）时需要
2. **pre/post hook payload**：hooks 框架的集成点
3. **`create_diff_consumer`**：用于 patch 类工具的 diff 追踪

### 5.3 DeepOmni 的 ToolOrchestrator

DeepOmni 已经有了 `ToolOrchestrator`，实现了 Codex 第五层的核心逻辑：

```rust

    pub fn evaluate(handler: &dyn ToolHandler, agent_mode: &AgentMode) -> OrchestratorDecision {

    pub fn evaluate_with_cache<K: Serialize>(

        // 先查 cache → 命中直接返回
        // 未命中 → 走正常 evaluate
    }
}
```

并且已经有了 `ApprovalStore`：

```rust
// crates/deepomni-tools/src/lib.rs (当前)
pub struct ApprovalStore {
    cache: std::sync::Mutex<HashMap<String, ApprovalDecision>>,
}

impl ApprovalStore {
    pub fn get<K: Serialize>(&self, key: &K) -> Option<ApprovalDecision>;
    pub fn put<K: Serialize>(&self, key: K, decision: ApprovalDecision);

```

DeepOmni 的 `ApprovalStore` 在核心接口上已经和 Codex 的功能等价（`get`/`put` + 序列化 key），但在使用方式上存在差异：

1. Codex 的 `ApprovalStore` 用 `with_cached_approval` 把 "查缓存 → 未命中则询问用户 → 缓存结果" 封装成一个原子操作
2. DeepOmni 的 `evaluate_with_cache` 只做了"查缓存"，但没有"缓存结果"的回写——回写发生在 `Runtime.approve_tool` 里，两者分离了

## 6. 第五层：审批与沙箱——集中到 Orchestrator

### 6.1 Codex 的 ExecApprovalRequirement

博客第 2 篇详细描述了 Codex 的审批和沙箱策略：

> `sandboxing.rs` 里有一个核心枚举：`ExecApprovalRequirement`。它把执行前状态分成三类：
> - `Skip`：不需要审批，可能还带 `bypass_sandbox`
> - `NeedsApproval`：需要用户或 guardian 审批
> - `Forbidden`：直接禁止

判断逻辑 `default_exec_approval_requirement` 结合 `AskForApproval` 策略和 filesystem sandbox policy：

```
Never / OnFailure         → Skip（不审批）
OnRequest + restricted FS → NeedsApproval
UnlessTrusted             → NeedsApproval（总是问）
Granular policy           → 可能 Forbidden
```

DeepOmni 的 `OrchestratorDecision` 枚举已经对应了这三种状态：

```rust
pub enum OrchestratorDecision {
    Proceed { sandbox_required: bool, escalate_on_deny: bool },
    NeedsApproval { reason: String, approval_id: String },
    Forbidden { reason: String },
}
```

### 6.2 Sandbox 不是开关，而是策略

博客强调了一个重要设计点：sandbox 不是"开或关"一个布尔值，而是一次执行尝试的策略——初始 attempt 是否 sandbox、失败后是否允许升级、额外权限是否被批准。

Codex 的 `SandboxAttempt` 支持：

```
第一次尝试 → sandbox 内执行
  ├─ 成功 → 返回结果
  └─ 失败（sandbox 限制导致）
       ├─ escalate_on_deny = true → 询问用户是否允许越过 sandbox
       │    ├─ 用户允许 → 非 sandbox 重试
       │    └─ 用户拒绝 → 返回 sandbox 错误
       └─ escalate_on_deny = false → 返回 sandbox 错误
```

DeepOmni 的 `Proceed { sandbox_required, escalate_on_deny }` 已经保留了这两个字段，但还没有实现 sandbox 重试逻辑。这是后续可以直接填充的。

### 6.3 apply_patch 为什么是一等工具

博客特别解释了为什么 `apply_patch` 不能只是 shell 里的一段命令：

> `apply_patch` 有独立 handler。同时 shell / unified exec 中如果检测到 `apply_patch` 命令，还会走 `intercept_apply_patch`。这个拦截很重要：否则模型可以把 patch 塞进 shell，绕过 patch 工具的语义、文件级审批、diff tracking 和安全评估。

`apply_patch` 一等化带来的好处：
1. patch 可以被解析成结构化文件修改
2. 审批可以按文件级别处理
3. TUI / app-server 可以展示 diff
4. rollout / trace 可以更准确记录"修改了什么"
5. shell 只是命令执行，不承担所有文件编辑语义

博客原文：

> 换句话说，Codex 不是只关心"最终文件变了"，它还关心"这个变更是通过什么语义边界产生的"。

这对 DeepOmni 的启示是：**file_write 和 shell exec 应该是独立的工具，不应该让模型通过 shell echo 来写文件**。DeepOmni 当前的 `file_write` 已经是独立工具，这是正确的。

## 7. 完整管线对比

### 7.1 三个项目的工具管线深度

```
Codex（5 层）:
  ToolSpec → ToolRouter → ToolCallRuntime → ToolRegistry → Orchestrator/Sandbox → Handler

Claude Code（2 层）:
  Tool.inputSchema → StreamingToolExecutor → Tool.call()

DeepOmni（当前，2.5 层）:
  ToolSpec → ToolRegistry.dispatch() → ToolOrchestrator.evaluate() → ToolHandler.handle()
```

### 7.2 每一层的价值

| 层 | 解决的问题 | DeepOmni 是否有 | 优先级 |
|----|-----------|----------------|--------|
| ToolSpec（模型可见 schema） | 控制模型看到什么工具 | ✅ `handler.spec()` | 已有 |
| ToolRouter（输出还原） | 多种工具来源统一成内部 ToolCall | ❌ | 中（引入 MCP 时需要） |
| ToolCallRuntime（并行控制） | 读并发、写串行 | ❌ | **高**（已有 trait 支持） |
| ToolRegistry（统一分发 + hooks） | 统一 telemetry、hooks、mutating gate | ⚠️ 部分（dispatch 有，hooks 无） | 中 |
| Orchestrator/Sandbox（审批+沙箱） | 集中审批和 sandbox attempt | ✅ `ToolOrchestrator` | 已有（sandbox 待实现） |

### 7.3 建议实施顺序

1. **ToolCallRuntime**（最高优先级）：DeepOmni 已有 `is_mutating()` 和 `supports_parallel()` trait 方法，只需要加一个 `RwLock<()>` 和 batch 执行逻辑。改动最小，收益最大。

2. **ToolRouter**（中优先级）：在引入 MCP 工具前完成。把 `ToolRegistry` 的 spec 管理和 dispatch 职责拆开。

3. **Registry hooks**（低优先级）：在 hook_dispatcher 集成点稳定后再加。

## 8. 设计理念总结

### 8.1 Codex 的核心理念

博客第 2 篇最后的总结：

> Codex 的工具系统可以概括成一句话：**模型输出只是一份工具调用意图；真正能不能执行、如何执行、在哪个权限和 sandbox 下执行，由 core 的工具运行时决定。**

关键分层是：
- `ToolSpec`：模型可见 schema
- `ToolRouter`：把模型输出还原成内部 `ToolCall`
- `ToolCallRuntime`：处理取消和并行
- `ToolRegistry`：统一 handler 分发、hooks、telemetry、mutating gate
- `ToolOrchestrator / sandboxing`：集中审批和 sandbox attempt
- handler runtime：shell、unified exec、apply_patch、MCP、dynamic tools 各自执行

> 这套结构的代价是文件多、调用链长；收益是安全策略、观测、并发和扩展都不需要散落到每个工具里。对 coding agent 来说，这个取舍很现实：工具能力越强，越需要把"能力"和"约束能力的边界"一起设计。

### 8.2 Claude Code 的核心理念

Claude Code 的工具系统更像 "application-level tool integration"：

- 一个 `Tool` 类型知道 spec、handler、permission、UI 呈现、abort control 等所有东西
- `StreamingToolExecutor` 提供了边流式边执行的能力
- 代价是工具和应用运行时强耦合

### 8.3 对 DeepOmni 的指导

DeepOmni 的工具系统已经有了很好的基础（`ToolHandler` trait 的 policy 声明方法、`ToolOrchestrator`、`ApprovalStore`）。最需要补充的是：

1. **ToolCallRuntime**：让已有的 `supports_parallel()` / `is_mutating()` 真正生效
2. **ToolRouter**：为 MCP 集成做准备
3. **把审批回写从 Runtime 移到 Orchestrator 附近**：当前审批缓存的回写在 `Runtime.approve_tool` 里，和 `ToolOrchestrator.evaluate_with_cache` 分离了
